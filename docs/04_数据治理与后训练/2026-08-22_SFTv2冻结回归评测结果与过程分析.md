# SFT v2 冻结回归评测结果与过程分析

日期：2026-08-22

状态：Base、SFT v1、SFT v2 均完成 18 任务 × 4 trials；基础设施失败已按整任务独立重跑替换

结论等级：开发级冻结回归证据，不是官方 benchmark、业务提升或生产发布结论

## 1. 结论摘要

在相同的 18 任务、4-trial、temperature 0、seed 20260818 协议下：

| 指标 | Base | SFT v1 | SFT v2 |
|---|---:|---:|---:|
| Trial 成功 | 37/72 = 51.4% | 48/72 = 66.7% | 48/72 = 66.7% |
| 四次均成功的稳定任务 | 4/18 = 22.2% | 8/18 = 44.4% | 8/18 = 44.4% |
| 至少一次成功的任务 | 14/18 | 15/18 | 14/18 |
| train_candidates trial 成功 | 15/28 = 53.6% | 20/28 = 71.4% | 20/28 = 71.4% |
| test_clean trial 成功 | 22/44 = 50.0% | 28/44 = 63.6% | 28/44 = 63.6% |

可以确认的开发级事实：

1. 两个 SFT checkpoint 相对 Base 都增加 11 个成功 trial（+15.3 个百分点），稳定成功任务从 4 个增至 8 个。
2. 加入六条所有者复核修正轨迹后的 SFT v2，没有在聚合成功指标上超过 SFT v1；二者均为 48/72、8/18。
3. 聚合持平掩盖了能力迁移。SFT v2 将 task 72、79 提升为 4/4，并修复 SFT v1 在 task 71 的回退；同时 task 100 从 Base 3/4、SFT v1 2/4 退化为 0/4。
4. SFT 并未降低总体 Tool Use。平均调用数 Base 6.43、SFT v1 7.12、SFT v2 8.10；SFT v2 的完全重复调用均值升至 1.18，并出现 task 77 trial 2 的 57 次调用。

因此，当前证据支持“首轮 SFT 学到了部分任务流程”，不支持“SFT v2 整体优于 SFT v1”，也不支持仅凭成功率立即启动 RL。

## 3. 基础设施失败与组合口径

Base 主运行 72/72 有效，无替换重跑。

SFT v1 主运行出现三个 `ContextWindowExceededError`：task 19 trial 2、task 43 trial 2、task 39 trial 1。按冻结协议，不只替换失败 trial，而是分别对 task 19、43、39 重新执行完整 4 trials，并用各自重跑产物替换主运行中该任务的全部四条记录。

SFT v2 主运行出现两个同类失败：task 18 trial 3、task 71 trial 2。处理方式相同，分别用完整 4-trial 重跑替换 task 18、71。

这使三个模型最终均为 18 tasks / 72 个有效 trials。重跑任务必须明确标记，因为外部 DeepSeek 后端不由仓库冻结；即使 temperature、seed 和配置相同，也不能把重跑理解成完全确定性复现。

## 5. Tool Use、时延与 token 诊断

| 指标（每个有效 trial） | Base | SFT v1 | SFT v2 |
|---|---:|---:|---:|
| 平均工具调用 | 6.43 | 7.12 | 8.10 |
| 工具调用中位数 | 6.00 | 7.00 | 6.50 |
| 平均读取调用 | 5.08 | 6.00 | 7.00 |
| 平均写入调用 | 1.35 | 1.12 | 1.10 |
| 平均完全重复调用 | 0.22 | 0.33 | 1.18 |
| 同工具最长连续调用均值 | 2.06 | 2.49 | 3.33 |
| 工具错误结果总数 | 46 | 31 | 35 |
| 平均耗时（秒） | 21.20 | 27.91 | 27.17 |
| Agent 消息观测 token | 95,656 | 95,089 | 120,724 |
| 用户模拟器消息观测 token | 11,441 | 7,661 | 15,036 |

工具数不能脱离结果比较。Base → SFT v1 的 30 个双方都成功 trial 上，平均调用从 6.17 降至 5.93（-0.23）；说明 v1 在不牺牲结果的成功切片上略有提效。Base → SFT v2 的 29 个双方都成功 trial 上，平均调用从 5.79 升至 6.24（+0.45），没有同样证据。

SFT v2 的 8 个回退 trial 平均调用比 Base 多 9.00 次，其中 task 77 trial 2 从 5 次增至 57 次。该轨迹是明确的停止/循环稳定性问题，不能被聚合成功率掩盖。

参考动作覆盖只能解释为 Tau2 reference action recall，不能解释为 Tool Precision。Base-vs-SFT v1 在 68 个参考动作可比 task-trial 对上的微平均召回为 73.1% → 86.9%；Base-vs-SFT v2 在另一组 65 个可比对上为 72.3% → 88.0%。两个切片的排除项不同，不能据此直接断言 v2 高于 v1。

Token 仅汇总 `returned_results.json` 的消息级 usage。assistant 对应本地 vLLM Agent，user 对应 DeepSeek 用户模拟器；NL Judge token 没有写入原始产物，序列化 cost 字段也不是可靠账单。因此本文不报告完整 DeepSeek token 或美元成本。

## 6. 对 SFT 瓶颈与 RL 门禁的判断

### 6.1 已学到的能力

- task 66、72、18、79、90 上出现跨多个 trial 的稳定改善，说明 SFT 已能学习部分工具选择、状态读取和业务流程模板。
- task 72、79 从 Base 0/4 发展到 SFT v2 4/4，是当前最强的正向证据。
- SFT v2 将 task 71 从 SFT v1 的 1/4 修复为 4/4，说明增量数据可能改变特定流程，但单任务变化不能单独归因于某一条训练样本。

### 6.2 仍未学稳的能力

- 停止条件与错误恢复：SFT v1/v2 均出现上下文溢出；SFT v2 还有 57 次工具调用的长循环。
- 稳定处理共同失败 task 19、39、74。
- 保持既有能力：task 100 随版本从 3/4 → 2/4 → 0/4，task 40 的 v1 增益也未被 v2 保留。
- 在正确结果之外控制冗余读取。SFT v2 的平均调用、重复调用和 Agent token 均明显高于 Base。

### 6.3 是否已经证明 SFT 达到瓶颈

尚未严格证明。SFT v2 与 v1 聚合持平是“可能进入边际收益下降”的信号，但本轮同时改变了数据量和样本曝光：47 行增至 53 行，训练 step 保持 80，单样本平均曝光下降。加上任务数只有 18、外部用户模拟器存在非确定性，不能把一次持平解释为普遍的 SFT 上限。

### 6.4 是否立即进入 RL

不应立即进入正式 RL。下一门槛不是继续堆 SFT 或直接套 GRPO，而是：

1. 审计共同失败 19/39/74，区分知识/流程缺失、环境或 benchmark 刚性、停止错误。
2. 审计 v2 回退与膨胀：100、50、77、40，并把 77 的 57-call 轨迹作为停止信号反例。
3. 用成功轨迹验证候选 reward 不会误罚必要读取，也不会奖励“少调用但提前失败”。
4. 只有当残余失败可被稳定、可验证的过程 reward 区分，且同任务能采样出有质量差异的多条 rollout 时，才进入 GRPO；若主要是固定格式或确定流程缺失，优先补高质量 SFT。

## 7. 结论边界

1. 18 个任务都用于过旧版开发评测，不是新鲜未见测试集。
2. 11 个 `test_clean` 来自官方 test split，但本项目已将其用于开发回归，不得称为官方榜单结果。
3. 重跑修复的是基础设施覆盖，不等于模型确定性增强。
4. Policy Grounding V2.2 尚无独立业务专家金标，只能作 provisional diagnostic。
5. 当前可发布的工程结论是：完成了冻结、多 trial、基础设施失败单列和整任务替换的 Base/SFT 回归，并发现成功率提升伴随工具调用膨胀及特定任务回退。不能发布“业务整体提升”或“已达到 RL 门禁”的结论。
