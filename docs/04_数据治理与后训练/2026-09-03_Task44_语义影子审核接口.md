- 选样：17 条此前存在争议的轨迹，加原始行 1、2 作为对照，共 19 条。
  这是有偏的开发诊断样本，不是独立测试集，不能报告总体准确率。
- 裁判输入：完整可见消息、工具参数和返回、消息索引、轨迹哈希和 policy。

- 裁判任务：每次写操作之前是否取得有效授权；所有 Agent 解释是否与当时工具

## 防护与已知限制

1. 原文件、policy、配置、代码的哈希写入 manifest；输出拒绝覆盖旧目录。
2. 裁判不接收原奖励标签；但完整对话中的工具成功信息仍可能影响判断。
3. JSON 多余字段、重复键、漏掉写调用、伪造引用、写后证据用于写前授权均拒绝。
4. API 错误、响应截断、结构不合法记 `ERROR` 并停止，不给 Agent 记低分。
5. 引用存在只证明可追溯，**不证明推理正确**。代码没有验证引用是否真正支持结论，
   也没有逐项证明事实审核覆盖了全部声明。提示注入防护目前主要靠角色隔离与提示，
   不能宣称完全免疫。
6. 写调用当前按消息位置审核；同一消息并行多个写调用只形成一条综合审核。
   不将此接口直接推广为通用逐调用合规判定器。
7. 语义不明使用 `UNCERTAIN`；无法靠降低阈值或多数投票自动升为真值。
8. 首批真实审核后，应对照原始证据复查规则/LLM 分歧；完成校准前不接入在线 Reward。
