## 3. 分层奖励

设各分量为已核验值，基础奖励为：

`R_base = 0.35E + 0.10T + 0.08I + 0.12Q + 0.20A + 0.15C`

| 分量 | 内容 | 判定责任 |
|---|---|---|
| E | 最终环境状态满足目标 | tau2环境结果与确定性状态证据 |
| T | 用户模拟器正常结束 | 确定性结束信号，不能用Agent自行结束替代 |
| I | 身份与订单归属 | 规则检查写前认证、归属证据及调用返回绑定 |
| Q | 取得目标订单/商品证据 | 规则核对调用参数和返回，不按调用次数累加 |
| A | 写入已获用户授权且参数一致 | 简单语义由规则；复杂确认由DeepSeek提取，再由规则对比写调用、价格差与实际退款 |
| C | 完成必要回复，且相关事实声明与已知状态一致 | 规则核对；复杂自然语言由DeepSeek转为带来源的类型化声明 |

A沿用PASS=1、REVIEW=0.5、FAIL=0的已有约定，且受有效写入、身份条件约束。
REVIEW表示业务语义存在不确定性，不等同于模型违规。API失败、解析失败、遗漏必审
候选属于评分不可用，不能伪装成REVIEW。

C涵盖写前解释和写后回复。已证实矛盾撤销0.15沟通分；没有声明不自动等于完成必要
沟通，没有检出错误也不能等于完整检查通过。若不确定项足以改变最终标量，本组先
不进入优化，保留待审证据。未知不自动记0，也不自动记1。

各里程碑每条轨迹最多计一次。重复查询、啰嗦回复不增加阶段分。

### 封顶和扣分

沿用已有数值和应用顺序：先按适用条件封顶基础分，再减工具/重复/长度惩罚，
执行额外写入硬封顶与最终[0,1]裁剪；已有运行时override最后保留。

- 无有效写入：至多0.25。
- 写入发生但身份不成立或授权FAIL：至多0.15。
- 授权REVIEW：至多0.75。
- 出现非预期写入：0。
- 终局成功但必要沟通不完整：至多0.9。
- 工具错误：每次0.03，最多0.09。
- 完全重复调用：每次0.02，最多0.06。
- 用户/工具调用上限：扣0.10。
- 单独工具迭代上限按现有冻结协议记0；超窗、异常截断、API和系统失败不能混成普通失败。

KL属于GRPO优化目标中的约束，不是上述业务奖励中的加分项。

## 4. “中间打分”如何进入现有GRPO

现有代码使用`RetailAgenticEnvironment.get_reward()`给每条轨迹返回标量；
trainer构造时`reward_funcs=[]`，不是额外再挂一个标准reward函数就会生效。
当前纯规则链为`get_reward -> _calculate_programmatic_reward ->
tiered_terminal_process_reward -> score_rollout`。

因此本次采取：

1. 保留各阶段事件及时间索引：认证、查订单/商品、确认、写入、回复。
2. 完整轨迹结束后，按每个事件当时可见的信息验证阶段分。
3. 必要时批量提交这一条轨迹的复杂语义候选给DeepSeek，最多一次。
4. 规则汇总阶段奖励，得到一个轨迹总分。
5. 同一组4条分数都就绪后，计算组内相对优势，才进入backward。

这是“包含过程分量的轨迹级GRPO”，**不是每个工具步骤各有独立advantage的过程级算法**。
阶段日志能解释哪个过程影响了分数，但不能声称已经解决精确的逐动作信用分配。
DeepSeek审核不反馈给运行中的Agent，不改动作、不重写轨迹。

## 5. DeepSeek的严格边界

模型固定`deepseek-v4-flash`，非思考模式、temperature=0、最多8192输出tokens，
60秒超时、无自动重试。同属DeepSeek的用户模拟器和评分辅助器是两个角色，但不是
跨厂商独立裁判。用户模拟器设置继续沿用原冻结绑定，不能顺带换版本。

DeepSeek只输出：同意/拒绝/新增条件、同意的参数、候选声明类型和值、不能确定的地方。
不输出总分、不选安全封顶、不计算退款、不判最终数据库是否正确。

### 修复已发现的声明遗漏

不能继续让LLM自由挑选“要审核哪些句子”。先由程序为Assistant文本的句子/列表项
建立带索引与原文位置的候选表。每个候选必须有结果；同一句中的早期错误和后续修正
都保留。金额、可用性、最低价等关键候选不能被无依据标成“无关”后静默跳过。
遗漏、无法绑定实体或语义不明必须显式输出，不能让194再次因漏提取而取得已验证满分。

候选ID在本地绑定原文与轨迹哈希，避免要求LLM完整复写长文本。
若返回quote，仍验证其存在；引用较长只告警，不将长度当语义错误。
这只降低已知风险，**不保证语义分类不会出错**，冻结后仍需抽查实际轨迹。

### 错误处理

- 四条中任一条出现API/协议/关键覆盖错误：保存整个待评分组，停止在更新之前。
- 不把错误设成0，不丢弃困难轨迹，不替换采样，不用重采样制造方差。
- 仅在轨迹、tokenization、策略和奖励哈希一致时，才允许对同一组补评分后续接。
  恢复接口尚未实装，不能承诺当前已具备这种精确续跑能力。
- 全组奖励相同可以合法存在：记录零标准差和无相对奖励信号，不自动扩大n；
  非零beta下仍可能存在KL项梯度，不能声称总梯度必为零。

以上区别于上一轮**离线**回退原分的策略。训练时不能静默让部分组员用规则分、
另一些用混合分，从而把审核器的技术失败当成行为差异。

- UNKNOWN不当成违规：用同一个合分函数计算可能分数范围。若范围不唯一则停止评分；
  若已确定的硬封顶使未知不影响总分，可以保留未知标记后释放该确定分数。

### 不扩大结论

覆盖检查不是通用语义正确性证明。未命中词形的改写、复杂指代及LLM错误标成NOT_IN_SCOPE
