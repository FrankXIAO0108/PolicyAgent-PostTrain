# 对抗评测集 V2 冻结协议

日期：2026-08-10

## 1. 为什么需要 V2

2026-08-02 云端工程实操只使用 24 条 SFT、24 对 DPO、8 条 GRPO prompt 和
8 条 holdout。原 holdout 虽然与训练集 scenario ID、订单 ID 不同，但复用了同一套
六类模板生成逻辑，因此 SFT 的 8/8 精确动作匹配只能证明同分布协议学习，不能证明
措辞、实体或风险组合变化后的泛化。

V2 的目的不是制造更高分，而是在下一轮训练或调参前冻结一个更难、泄漏风险更低的
开发者合成评测集，用来暴露工具协议漂移、范围扩大、缺参猜测和提示注入问题。

## 2. 数据边界

- 范围：`ISOLATED_EVALUATION_ONLY`；
- 数据来源：开发者编写的合成场景；
- 数量：48 条，8 类能力，每类 6 条；
- 与 tau2 冻结任务隔离，不包含正式 Retail 轨迹；
- 不是独立人工 gold，不允许声明生产指标或 Retail 业务提升；
- 明确设置 `training_use_prohibited=true`，不得进入 SFT、DPO 或 GRPO 数据。

## 3. 能力分层

| 类别 | 主要检查点 |
|---|---|
| read_only_query | 只读请求不产生写副作用 |
| confirmation_before_write | 未授权时先确认 |
| missing_required_argument | 地址缺失时不猜测 |
| check_before_mutation | 换货前先检查变体可用性 |
| refund_method_grounding | 不默认退款方式 |
| no_unsupported_guess | 无法补齐目标规格时转人工 |
| scope_preservation | 商品级请求不扩大为整单操作 |
| registry_injection | 忽略用户要求的虚构工具名、额外文本或多次调用 |

## 4. 冻结与泄漏检查

生成器必须记录：

1. 评测文件 SHA-256；
2. 每类样本数；
3. 与 V1 的 scenario ID 重叠；
4. 与 V1 的完整 prompt 重叠；
5. 新实体前缀隔离；
6. 数据仅用于 evaluation 的声明。

只有 manifest 中 `leakage_checks.passed=true` 时，V2 才可用于下一轮冻结比较。
评测结果必须同时报告总体指标和分类别指标，并区分“可提取 JSON”与“严格唯一
JSON”。

## 5. 使用顺序

```text
提交并冻结 V2 数据与哈希
→ 在不改训练的情况下评测已有 Base/SFT/DPO/GRPO
→ 形成失败矩阵
→ 根据失败矩阵设计 DPO hard negative 与 GRPO reward
→ 训练新变体
→ 仍在同一冻结 V2 上比较，但不得继续针对单条样本改数据
```

若已有云端 adapter 不可恢复，应先重新生成同配置 checkpoint；不得根据 V2 结果
修改 V1 冻结产物或补写历史指标。
