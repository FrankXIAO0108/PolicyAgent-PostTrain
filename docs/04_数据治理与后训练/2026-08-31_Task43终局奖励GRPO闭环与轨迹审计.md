# Task 43 终局奖励 GRPO 闭环与轨迹审计

日期：2026-08-31
状态：开发实验完成；泛化与业务提升未验证

## 1. 实验目的

本轮只验证一件事：在 Qwen3-4B 的真实 Retail 多轮 Tool Agent 环境中，纯终局环境状态奖励能否完成一次可审计的 GRPO 参数更新闭环。

闭环定义为：

```text
SFT merged checkpoint
-> 同任务多条在线 rollout
-> tau2 环境执行与 DB 状态检查
-> 组内相对优势
-> 反向传播与 LoRA 参数更新
-> adapter 保存与模型合并
-> 同协议训练后采样
```

本轮不用于证明终局奖励优于分层奖励，也不用于证明模型获得跨任务泛化提升。

## 3. Task 43 的实际目标

用户需要：

1. 使用姓名和邮编完成身份定位；
2. 查询两个候选订单；
3. 告知女儿订单的地址、tracking number、配送状态和 tablet 的 64GB 存储；
4. 在用户明确确认后，将默认地址改为 Chicago 地址。

关键 Policy：写数据库前必须列出操作细节并取得明确确认；一次最多调用一个工具；调用工具时不得同时向用户输出文字；不得编造工具未提供的信息。

## 4. GRPO 参数更新证据

- 模型：Qwen3-4B，BF16 LoRA；未量化。
- `max_steps=2`，`num_generations=2`，共 2 组、4 条 rollout。
- Reward：仅 `terminal_environment_state`，其余过程项权重及惩罚均为 0。
- 第 1 步组内 reward 全为 1，标准差为 0，没有有效相对优势。
- 第 2 步 reward 为一正一负，产生非零相对优势。
- 实际 optimizer step：2/2；其中 1 步出现非零梯度，`grad_norm=0.0604860932`。
- 起始与结束 adapter 权重 hash 不同，参数更新已由优化证据确认。
- KL 配置 `beta=0.02`，日志中两步 KL 均为 0；只能证明 KL 路径被记录，不能声称本轮观察到非零 KL 约束效果。
- 训练中出现两次 CUDA allocator OOM 警告，但运行继续并完成；4090 24GB 的显存余量很小。

结论：真实 GRPO 工程闭环成立。该结论只指参数更新链路成立，不等于策略质量提升成立。

## 7. 对终局 Reward 的判定

终局 Reward 在本任务上能区分“是否最终完成地址写入”，因此不是无效信号；训练中确实产生了一组非零相对优势。

但它存在三个确定缺口：

1. 看不到中间事实幻觉：GRPO-0 的错误 tracking 声明仍得 1 分。
2. 不约束路径效率：GRPO-1 的重复信息读取仍得 1 分。
3. 不区分合规完成与仅状态完成：本轮写前确认恰好正确，但 confirmation 未进入 scalar reward。

因此，纯终局 Reward 适合作为闭环对照组，不适合作为最终训练信号。

## 8. 下一步门槛

下一步不是扩大训练步数，而是在完全相同的 Task 43、SFT 起点、采样配置和训练预算下，定义分层 Reward 对照版本。至少需要独立表示：

- terminal DB success；
- 必需信息是否由成功工具结果支撑；
- 写前明确确认与参数绑定；
- 必需动作进度；
- 工具错误、重复调用和无关调用；
- 事实冲突或 unsupported claim。

在任何再次训练前，先用本轮 4 条训练 rollout 和 4 条前后采样轨迹做离线排序检查：分层 Reward 必须把“完整、合规、事实一致”的轨迹排在“仅终局成功但有事实错误”的轨迹之前，并且不能把未完成写入的 SFT-0 排成成功。

### 8.2 Group size 诊断

本轮 terminal-only 4 条 rollout 的观测成功率为 0.75。若临时假设同一 prompt 的各次采样独立、策略在采样期间不变、Reward 为二值，则 group size 为 `n` 时产生 mixed group 的概率为 `1-p^n-(1-p)^n`：

| n | 预计 mixed-group 概率 |
|---:|---:|
| 2 | 0.375000 |
| 4 | 0.679688 |
| 8 | 0.899872 |

因此 `n=4` 是相对 `n=2` 的最小单变量诊断升级，但按该点估计尚不能达到 80% mixed-group 概率；候选集合 `{2,4,8}` 中最小达到 80% 的是 `n=8`。该结论不能直接作为正式超参数选择：样本仅 4 条，且两个组之间发生了参数更新，独立同分布与策略平稳假设并不严格成立。下一轮先执行 `n=4`，实测 mixed-group、零标准差、显存和生成成本，再决定是否升至 `n=8` 或改用中等难度任务/动态采样。证据文件：`tmp/cloud_results/20260831-task43-terminal-grpo2step-v1/local_audit_group_size_forecast_v1.json`。

### 9.5 确认参数绑定 v4 的离线对照

## 10. 当前闭环结论

截至 2026-08-31，真实 Agent GRPO 的工程闭环已经完成，不应再表述为“尚未跑通过一次 GRPO”：

- terminal-only n4：2 个 optimizer step、8 条 rollout、2/2 mixed group、2/2 非零梯度 step、LoRA 参数变化、adapter 与 merged model 均已保存；
- staged-confirmation v4 n4：同样完成 2 步真实优化和模型保存；
- 两次运行均记录 `beta=0.02` 的 KL 路径，末步 KL 分别为 `0.000448` 和 `0.000604`；
- terminal-only 的 6/8 terminal success 只能视为该训练批次的 rollout 结果，不是训练后泛化指标；
- v4 的 0/8 terminal success 与 8/8 正训练奖励证明 Reward 对齐失败，因此 v4 是失败实验，不是质量改进。

当前未完成的是“可信效果闭环”：尚无相同冻结评测协议下足够样本量的 SFT vs terminal-GRPO vs 分层-GRPO 对比，也没有证据支持 v5 在线训练。后续顺序应为：先完成同协议评测和 badcase 对照；再决定是补采完整 v5 质量组，还是把 4096-token 预算耗尽正式定义为部署失败并冻结该语义。不得一边观察当前轨迹一边临时改变截断标签。
