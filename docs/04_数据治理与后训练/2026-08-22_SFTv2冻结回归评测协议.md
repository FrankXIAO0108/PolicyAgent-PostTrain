# SFT v2 冻结回归评测协议

## 1. 目的

本协议在运行 owner-corrected SFT v2 训练之前冻结评测任务、实体隔离范围、模型对照组和统计口径，避免根据训练结果事后挑选任务或修改成功标准。

本评测只支持开发级回归结论。18 个任务都曾用于此前的 SFT v1 开发评测，因此不是全新未见测试集，不支持正式业务提升、生产门禁或 leaderboard 声明。

## 2. 为什么从 30 个任务缩减到 18 个

旧配置 `retail_teacher_eval_v1.json` 针对 47 条 Teacher SFT 数据冻结了 30 个实体隔离任务。加入六条所有者复核修正轨迹后，训练集扩大到 53 条，旧任务中出现两类污染：

1. Task `36/38/59/76/101/105/107` 直接参与修正或数据角色决策。
2. Task `37/67/64/68/102` 与新增训练轨迹共享订单、用户或商品实体。

从上游 Retail 的全部 74 个 train 任务和 40 个 test 任务重新检查后，严格实体隔离只剩：

- train_candidates（7）：`19, 24, 43, 50, 66, 72, 89`
- test_clean（11）：`18, 39, 40, 65, 71, 74, 77, 79, 90, 100, 108`

不存在可以在不放松当前实体隔离规则的情况下补入的新任务。为了凑数量重新加入重叠任务会制造训练泄漏，因此本轮接受 18 题规模限制。

## 4. 指标口径

### 4.1 主指标

- trial-level success rate：成功 simulation 数 / 有效 simulation 数；每个模型最多 72 个有效 trial。
- all-trials task success：一个任务四次均成功才计为稳定成功；最多 18 个任务。
- infrastructure coverage：基础设施失败不混入模型失败分母，必须单列并补跑。

### 4.2 诊断指标

- any-trial task success：四次中至少成功一次，只用于观察能力上限和方差。
- train_candidates / test_clean 分层 trial 成功率。
- Base → SFT v1 → SFT v2 的逐任务翻转与回退。
- 平均、分位数和逐任务 Tool Use 次数，由已有 teacher eval card 工具从原始轨迹计算。
- Outcome、Action、Policy、State、Claim Consistency 等过程维度继续作为诊断信号，不能替代 tau2 task reward。

不得只报告 any-trial 成功率，也不得用一次偶然成功掩盖另外三次失败。

## 5. 可解释性边界

本轮可以回答：

> 在同一 Qwen3-4B 基座、相同 80-step 训练预算和冻结的 18 任务四次回归协议下，加入六条所有者复核修正轨迹后，SFT v2 相对 Base 和 SFT v1 的开发级任务成功、稳定性及 Tool Use 行为发生了什么变化。

本轮不能回答：

- SFT v2 在全体电商业务上的真实提升幅度。
- Verifier 的正式 Precision / Recall / F1。
- 模型在完全未见任务上的泛化能力。
- 是否已经满足生产发布或正式 RL 门禁。

如果需要真正未见的最终测试，必须新增经过独立冻结、实体不重叠的任务集，或者重新规划训练/评测切分；当前 tau2 Retail 目录中已经没有满足现有隔离条件且未被旧开发评测使用的任务。

## 6. 执行顺序

1. 提交本协议、v2 配置、实体清单及评测器测试。
2. 云端上传 53 条冻结数据并运行 SFT `validate-only`。
3. 运行 SFT v2，保存 adapter、merged model、训练日志和 run manifest。
4. 将训练 manifest 中的 merged model SHA-256 绑定到 v2 评测配置并单独提交。
5. 每个模型先跑一个独立 smoke 任务，输出目录不得复用。
6. 依次运行 Base、SFT v1、SFT v2 的 18 × 4 完整评测。
7. 保存原始 returned_results、eval_summary、run_manifest，再生成对比表和过程指标。
8. 根据残余系统性失败及 Reward/Verifier 的可靠性决定是否进入 DPO 或 GRPO，不因“已经设计过 RL”而强行启动。
