# 教师 SFT 多种子稳定性与扩窗补跑报告

日期：2026-08-21
状态：开发级稳定性证据；不是正式 Retail 门禁或 tau2 官方榜单结果

## 0. 结论

同一份 34 行教师 SFT 数据、相同 80 steps、三个训练 seed 的实体隔离 validation
assistant loss 为 `0.4105 / 0.4114 / 0.4107`，已经高度接近。仅看 teacher-forcing loss，
80-step 全量 SFT 可标记为 `SFT_PLATEAU_CANDIDATE`。

但真实 30-task 多轮评测没有同样稳定：

- 历史 seed 20260818 的修正组合结果为 `17/30`；
- seed 20260819 的原始单次全量结果为 `15/30`；
- seed 20260820 只有 `28/30` 得到有效 reward，结果为 `16/28`，task 100、102 是
  `ContextWindowExceededError`，不能按普通模型失败计算；
- 在 `max_model_len=49152` 下对两个 seed 成对重跑 task 100、102 后，开发级组合结果均为
  `16/30`，但逐任务只在 `22/30 = 73.3%` 上一致，仍有 8 个成功/失败翻转。

因此，当前证据支持的不是“已经完成稳定 RL 前置门禁”，而是：

1. 继续重复相同 SFT 配方的边际价值已经较低；
2. outcome 对训练 seed、外部用户模拟器和长轨迹生成具有明显方差；
3. SFT 能提高相对 Base 的任务成功，但过程调用仍偏长，且 loss 不能预测单任务成败；
4. 可以进入**有约束的过程奖励设计与离线验证**，但在 verifier/reward 通过抗钻空子检查前，
   不能直接把 provisional policy 规则接入正式 GRPO。

### 3.1 补跑边界

seed19 的 task100 在原 24576 运行中是普通 reward 0，在 49152 补跑中变成 reward 1；task102
保持 reward 0。这说明补跑结果不只是“修复 seed20 的超窗”，还叠加了多轮 rollout 与外部
用户模拟器的非确定性。因此，下节的 30/30 是**开发级组合视图**，不能冒充相同服务参数下的
一次连续全量运行。

## 4. 开发级组合 30/30 视图

组合规则：seed19 用 49152 的 task100、102 替换原 task100、102；seed20 在原 28 个有效结果上
加入两个 49152 补跑结果。

| 指标 | seed19 组合 | seed20 组合 |
| --- | ---: | ---: |
| 成功任务 | 16/30 = 53.3% | 16/30 = 53.3% |
| train_candidates | 7/13 = 53.8% | 7/13 = 53.8% |
| test_clean | 9/17 = 52.9% | 9/17 = 52.9% |
| 平均工具调用 | 8.13 | 8.77 |
| 工具调用总数 | 244 | 263 |
| Tool error 总数 | 13 | 18 |
| 平均 Tool error | 0.43 | 0.60 |
| 平均 Agent turn | 15.43 | 16.27 |

两个模型的聚合成功数完全相同，但这不代表行为稳定：

- 成功/失败一致：`22/30 = 73.3%`；
- 成功集合 Jaccard：`0.60`；
- 发生翻转的 8 个任务：`59、67、72、107、64、79、101、100`。

这个结果说明 30-task 单 trial 的分辨率有限。只报告 `16/30` 会隐藏任务级方差，也不足以判断
某个 checkpoint 在特定业务类型上更可靠。

## 5. 与历史 Base / seed18 的关系

历史冻结开发证据为：

| 模型 | 成功 | 平均工具调用 | 证据性质 |
| --- | ---: | ---: | --- |
| Qwen3-4B Base | 12/30 = 40.0% | 6.63 | 单次 30-task |
| SFT seed18 修正组合 | 17/30 = 56.7% | 9.43 | 原 28 条 + task100/107 独立重跑 |
| SFT seed19 扩窗组合 | 16/30 = 53.3% | 8.13 | 原全量中替换 task100/102 |
| SFT seed20 扩窗组合 | 16/30 = 53.3% | 8.77 | 原 28 条 + task100/102 补跑 |

三次 SFT 开发视图都高于同一历史 Base 的 12/30，说明 SFT 的正向作用不是只由 seed18 的单次
偶然结果支撑。但这些 SFT 数字包含不同上下文上限下的组合证据，外部用户模拟器后端也无法冻结，
因此不能据此计算严格的均值、标准差或置信区间，也不能宣称正式业务提升。

更稳定的共同现象是：SFT 后平均工具调用仍高于 Base。seed19、seed20 相比 seed18 略低，
但没有回到 Base 的 6.63；这支持把“停止条件、查询剪枝、错误恢复”作为下一阶段目标，而不是
继续只优化最终答案格式。

## 6. 对 SFT 与 RL 路线的判断

### 6.1 已确认事实

1. 三个训练 seed 的 validation assistant loss 极接近，重复相同 80-step SFT 配方不太可能带来
   明显的 teacher-forcing 改善。
2. 真实多轮 outcome 仍有较大任务级方差，loss 平台不等于行为平台。
3. SFT 相比 Base 提高了开发任务成功数，但过程更长，工具错误没有稳定消失。
4. 一些残余问题属于停止、重复调用、错误恢复和写操作约束，单纯增加“正确轨迹样式”的收益有限。

### 6.2 尚未确认

1. 没有证明 GRPO 一定优于继续补充高质量纠错 SFT；
2. 没有经独立业务专家确认的 policy gold，Policy Grounding V2.2 仍是 provisional diagnostic；
3. 没有完成 reward hacking、错误惩罚导致提前停止、调用数惩罚导致漏查等反事实测试；
4. 没有正式多 trial 冻结结论，外部用户模拟器本身也是 outcome 方差来源。

### 6.3 下一步门禁

下一步不应继续盲目增加训练 seed，也不应直接跑大规模 GRPO。合理顺序是：

1. 用当前失败/翻转任务构建过程级 error taxonomy：无效查询、重复调用、工具错误后重试、
   未确认写操作、状态与最终回复不一致；
2. 为每类错误定义可程序化验证的硬信号和反事实 case；
3. 在当前 Base/SFT 原始轨迹上离线回放 reward，检查是否误罚成功轨迹、是否奖励提前停止；
4. 只有硬约束达到可接受 precision，才做小规模 GRPO smoke；
5. GRPO 与继续纠错 SFT 使用相同冻结任务、相同过程 Evaluation Card 比较，不能只报最终 reward。

## 8. 可发布的准确结论

> 我没有把单次 SFT 提升直接解释成稳定收益，而是在同一 34 条教师轨迹、80 steps 下补做三个
> 训练 seed。三个 seed 的实体隔离 validation loss 稳定在约 0.411，但两个新增 checkpoint 在
> 30 个 Retail 多轮任务上虽然组合成功数都为 16/30，逐任务一致率只有 73.3%，并且平均工具调用
> 仍高于 Base。实验说明 token-level SFT loss 平台并不等价于 Agent 行为稳定，因此我把下一阶段
> 从“继续重复 SFT”转为过程 reward 的离线验证：先验证停止、重复调用、工具错误与写操作约束的
> precision 和抗 reward hacking，再决定是否启动小规模 Agentic GRPO。

不能表述为“已经证明 SFT 到达理论瓶颈”“已经完成正式 Retail RL 门禁”或“多 seed 平均成功率
稳定提升”，因为当前组合结果的服务参数并非完全一致，且只做了每 checkpoint 一个 rollout trial。
