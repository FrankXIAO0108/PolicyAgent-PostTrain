> environment-state reward shortcut。当前必须先完成 Tool SFT，并验证 action-progress

## 1. 结论与边界

本项目中的 Agent 是一个**电商售后 Tool Agent**，不是商品推荐聊天机器人。它基于
tau2-bench Retail 环境处理用户身份查询、订单查询、取消订单、修改地址/商品/支付方式、
退货、换货和人工转接等任务。Agent 的动作会真实改变一份隔离的 Retail 数据库状态，
所以最有价值的训练信号不只是最终回答，而是整个“询问—查库—确认—写操作—核验”过程。

本设计实现的是一条隔离的 Agentic RL 工程路线：

```text
已完成的 Qwen2.5-0.5B SFT checkpoint
→ 真实 tau2 Retail 多轮环境
→ 4 条同任务 rollout 组成一个 GRPO group
→ 过程证据 + 最终数据库状态组成轨迹奖励
→ LoRA Agentic GRPO
→ 保存 adapter、merged model、原始轨迹、训练日志和哈希
```

它当前**不打开正式 Retail 后训练门禁**。原因是现有 20 条开发轨迹仍没有独立双人盲审
形成的政策金标。当前运行只能表述为“在隔离的 Retail train split 上完成真实多轮
Agentic GRPO 工程实操”，不能表述为“已证明线上业务提升”。

## 2. 为什么中间过程比只看最终答案更重要

电商售后任务具有不可逆或高风险写操作。两个 Agent 最后都可能说“已经处理好了”，但
中间过程可能完全不同：

- 一个 Agent 先验证身份、读取订单状态、向用户复述准确变更、得到明确确认后再写库；
- 另一个 Agent 猜测订单号、跳过确认、重复扣款或修改错误订单，最后仍声称成功；
- 还有一种情况是工具调用成功，但最终数据库状态不符合用户真实意图。

因此只训练最终自然语言会留下三类盲区：

1. **False Success**：说成功但数据库没有达到目标状态；
2. **Policy Violation**：目标完成了，但授权、确认或工具边界违规；
3. **Reward Hacking**：通过重复调用、命中宽松规则或输出讨好 Judge 的文字刷高分。

本项目把一次完整 rollout 保存在 `raw_rollouts.jsonl`，奖励从轨迹中的实际工具调用、
工具错误、最终数据库状态和必要沟通项计算，而不是只评分最后一句话。

## 3. 环境、状态、动作与观测

### 3.1 环境

`src/rl/retail_agentic_env.py` 将固定 commit 的 tau2 Retail 环境包装为 TRL
`environment_factory`。每一条 rollout 都创建独立环境实例并从任务 `initial_state`
重置数据库，避免不同 rollout 相互污染。

### 3.2 Agent 可观察状态

Agent 可以看到：

- Retail policy；
- 已冻结的首条用户话术；
- 自己此前的客户沟通；
- 工具返回的订单、用户、商品和数据库结果。

Agent 看不到：

- `task.user_scenario` 隐藏指令；
- gold action 列表；
- 最终数据库断言；
- reward 计算细节。

隐藏信息只存在于用户模拟器和奖励环境内，不能进入模型 prompt。

### 3.3 动作空间

动作空间由 16 个 Retail 工具与一个客户交互工具组成。只读工具用于查询用户、订单、
商品和变体；写工具用于取消、修改、退换货；`respond_to_user` 用于澄清、复述和请求确认，
并返回动态客户的下一轮话术。

模型每轮可以：

```text
调用 Retail 工具 → 获得数据库观测
调用 respond_to_user → 获得客户观测
输出非工具终止消息 → 结束 rollout
```

### 3.4 动态客户

首条客户话术先以温度 0 生成并冻结，保证同一任务的四个 GRPO generation 拥有同一起点。
后续客户回复由隐藏场景驱动的 tau2 user simulator 生成。`user_seed` 在同组内保持一致；
由于远程模型服务仍可能存在非确定性，这部分噪声必须通过原始轨迹和多 seed 评测观察。

## 4. 过程奖励 V1

### 4.1 基础奖励

只对当前任务实际适用的项做权重归一化：

```text
R_base = normalize(
    0.70 × R_environment_state
  + 0.20 × R_required_action
  + 0.10 × R_communication
)
```

- `R_environment_state`：用 tau2 程序化 EnvironmentEvaluator 检查最终数据库状态；
- `R_required_action`：gold assistant actions 的一对一匹配召回率；
- `R_communication`：仅在任务存在结构化 `communicate_info` 时计算。

自然语言 LLM Judge 不进入在线 reward。这样可以避免额外推理费用、Judge 漂移和模型通过
措辞迎合 Judge。

### 4.2 为什么重写动作进度匹配

上游 benchmark 的动作检查适合判断“金动作是否出现过”，但一个预测调用可能同时命中
多个重复金动作。用于 RL 时，这会给模型留下重复信用漏洞。

本项目实现 `one_to_one_action_progress`：一个实际调用一旦匹配一个预期动作，就不能再次
匹配另一个预期动作。重复调用超过 gold multiplicity 时计入惩罚。这是 benchmark 复现
逻辑和训练 shaping 逻辑之间有意保留的差异。

### 4.3 惩罚项

```text
R = clip_0_1(
    R_base
  - min(0.20, 0.05 × tool_error_count)
  - min(0.15, 0.03 × repeated_call_excess)
  - min(0.20, 0.05 × unexpected_write_count)
  - 0.10 × unfinished_interaction
)
```

- 工具错误惩罚：抑制无效参数、错误状态下调用和盲目试错；
- 重复调用惩罚：抑制循环和重复刷动作信用；
- 非预期写操作惩罚：写库动作未匹配任何 gold action 时扣分；
- 未完成交互惩罚：客户没有进入 stop 状态就结束时扣分。

### 4.4 暂不进入 reward 的信号

以下信号只记录诊断，不参与 V1 奖励：

- Policy Guard findings；
- 基于关键词检测的“写操作前明确确认”；
- LLM Judge 的自然语言断言。

原因不是它们不重要，而是当前没有独立人工金标证明其 precision/recall 足以作为训练权威。
把高误报规则直接放入 RL，会让模型学习绕规则而不是真正遵守业务政策。待双人盲审金标完成
后，再决定是否升级为 Policy-aware reward。

## 5. 这是不是“真正的中间过程 RL”

这是**多轮环境交互 + 轨迹级过程塑形的 Agentic GRPO**：模型在 rollout 中连续调用工具，
每次动作改变后续观测；环境最后把中间过程证据汇总成一个标量 reward，TRL 再对该条轨迹
中的模型 token 做 GRPO 更新。

它不是带 Value Model 的 PPO，也没有对每个工具步骤分别估计 step advantage。因此面试中
应准确表述为：

> 我把电商 Agent 的 DB 终态、必要动作进度、沟通完成度、错误与重复调用组成轨迹级
> process-shaped reward，在真实多轮 Retail 环境上做 Agentic GRPO。

如果未来需要真正的逐步 credit assignment，才进一步引入 step verifier、逐步 reward、
critic/value model 或自定义 PPO rollout buffer；当前 0.5B/10-step 实验不应包装成该能力。

## 6. 数据划分与防泄漏

固定上游 commit：`58e5e1ace69302e6982d27014569c03e0ffccdd2`。

74 条 Retail train tasks 被一次性冻结为：

- 44 条 `rl_train`：本次 Agentic GRPO；
- 10 条 `rl_validation`：训练后 Base/SFT/GRPO 比较；
- 20 条 `development_audit`：此前 Prompt Baseline 与失败分析，禁止进入 RL。

官方 40 条 test tasks 保留到最终评测，不在代码输出中展开 ID，只保存 ID 列表哈希和
零重叠检查。任务划分证据位于 `data/retail_agentic_rl_v1/task_split.json`。

一个重要限制是：训练 reward 使用任务 gold actions。它能提供低成本过程信号，但也可能
偏向唯一参考路径，惩罚其他业务上等价的正确路径。因此它只占 0.20 权重，并且最终结论
必须由未参与训练的 validation 和人工 case review 支持。

## 7. GRPO 训练配置

- 起点：2026-08-02 云端实跑得到的 SFT merged checkpoint；
- 模型：Qwen2.5-0.5B-Instruct；
- 参数高效训练：LoRA，`r=16`、`alpha=32`；
- 单卡：RTX 4090 24GB，bf16；
- 正式工程 run：10 optimizer steps；
- 每组：4 generations；
- 最大 completion：512 tokens；
- KL：`beta=0.02`；
- loss：`dr_grpo`；
- 不启用 vLLM，不安装 flash-attn；
- 每条轨迹最多 8 次客户回复、32 次 Retail 工具调用、40 次总工具迭代。

选择 SFT checkpoint 而不是此前 DPO/单轮 synthetic GRPO checkpoint，是因为旧 8 条
holdout 上 SFT exact action match 为 100%，后续 DPO 和 GRPO 都回落到 50%。本次目标是
从目前证据最好的工具协议起点学习真实交互，而不是继承已观察到的退化。

## 8. 反 Reward Hacking 设计

训练前和训练后必须检查：

1. 一个调用不能重复匹配多个 gold action；
2. 超额重复调用会扣分；
3. 未匹配的写操作会扣分；
4. 工具报错会扣分；
5. 客户未停止就结束会扣分；
6. reward 不读取模型最终自述的“成功”；
7. Policy Guard 和确认规则在未验证前不能成为 reward authority；
8. 所有 rollout 原文、reward breakdown、模型哈希和配置哈希必须保存；
9. 观察 `reward_std`：同一 group 全部同分时 GRPO 没有有效相对优势；
10. 对高 reward 轨迹人工抽查，防止 gold path 命中但用户意图或政策仍错误。

## 9. 验收标准

### 工程验收

- 本地 environment-only preflight 通过；
- 云端 CUDA、TRL `environment_factory`、Transformers>=5.2、jmespath 检查通过；
- tokenizer 可以渲染 tool schema；
- 1-task/1-step sanity run 保存 4 条左右真实 rollout；
- 10-step run 保存 adapter、merged model、logs、metrics、raw rollouts 和 SHA-256；
- 至少部分 group 出现非零 reward 方差，否则只能证明流程运行，不能证明发生有效 GRPO 学习。

### 效果验收

训练完成后，使用 10 条 `rl_validation`，在同一客户 opening、seed、最大轮数和解码协议下
比较 SFT 与 Agentic-GRPO：

- DB task success；
- required action recall；
- tool error / repeated call / unexpected write；
- 平均轮数、token、延迟和 API cost；
- confirmation/Policy Guard 诊断；
- 人工抽查高 reward 与失败 case。

只有验证集改善且没有安全指标退化，才值得扩大 steps、任务数量或模型规模。官方 test 仍
不能用于调参。
