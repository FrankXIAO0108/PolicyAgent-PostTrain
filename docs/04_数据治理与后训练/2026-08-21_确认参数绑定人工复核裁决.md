## 4. 与 Codex 预标注的差异

18 条中 15 条一致，3 条被人工修正：

1. `105:run_a` ACCEPTABLE → POLICY_VIOLATION：用户确认"1.5L 燃气壶"，
   实际写入 item 是 1L，成功写入的 ID 与确认的语义条件冲突；
2. `107:run_a` 两条 ACCEPTABLE → ACCEPTABLE_CUMULATIVE：先前的错误订单关联与
   重复失败写让"确认绑定"只在累计语义下成立，且整条轨迹必须修正。

## 5. 关键模式（供 Verifier/Reward 与修正模板使用）

1. **绑定成立 ≠ 整条轨迹合格**：36/37/38/79/100/101/107 的写参数均被判定为已确认，
   失败责任在目标错误、实体选择、环境损坏或通信失真，不在"缺确认"。确认诊断不能
   单独作为轨迹质量判定。
2. **POLICY_VIOLATION 的形态**：未确认的取消 reason（59）；空替换项 + 未确认支付
   （76）；未复述订单/附带商品/原因即取消、自造 reason（76）；写入 ID 与已确认
   语义条件冲突（105）；1 条未评严重度（19）。
3. **环境损坏（CORRUPTED_TOOL_RESULT）**：37 两处、100 一处，均按 MIXED_HOLDOUT
   处置，不进入正/负样本。
4. **benchmark 冲突**：38（STATIC_GOLD_CONFLICT：用户与静态 gold 对 reason 要求
   相反）、79（SIMULATOR_GOLD_CONFLICT：话术自相矛盾）——这类轨迹不能按 reward 0
   朴素学习为负例。
5. **RAW_GOLD 候选**：79:run_b 是唯一整条合格候选，但 task79 位于冻结评估集，
   进入训练前必须先做 split 变更记录；不能边训边用同一任务报改进。

## 6. Reward 集成结论

`reward_integration_allowed=false` 维持不变。原因（照录绑定摘要）：
合成契约全等匹配不能证明真实轨迹精度；成功轨迹仍含 REVIEW 与 NOT_EVALUABLE 写操作；
地址参数仍在 v1 契约之外。本轮裁决只标定真实轨迹的确认绑定语义，不打开 Reward 集成。
