## 0. 口径修正与所有者决策

本文件最初把“干净最终测试”默认定义为 task、用户、订单和商品实体均与训练数据隔离。该定义适合 entity-OOD 泛化，但比当前项目需要回答的问题更严格。2026-08-23 经所有者确认，当前主线采用两级口径：

1. 项目内部最终评测：task-unseen、允许 entity overlap；
2. 可选严格评测：task-unseen 且 entity-disjoint，留作后续增强，不作为当前训练前置条件。

因此，下文严格污染审计及反向排除成本继续保留为证据，但“必须删除实体重叠训练数据并重训”不再是当前主线结论。

## 1. 审计问题

本审计回答：在当前 SFT v2 数据和既有开发评测已经发生后，上游 Retail official test 中是否仍存在同时满足以下条件的任务：

1. 未参与开发评测；
2. task ID 未进入 SFT 数据；
3. 用户、订单、商品等实体不与 SFT 数据重叠。

“对旧任务重新 rollout”只产生新轨迹，不会消除任务与规则开发污染，因此不满足最终评测要求。

## 4. 原因

此前 Teacher Eval 是在训练数据冻结后，从 official test 中选择实体隔离任务。17 个当时实体隔离的 test task 随后全部用于开发评测；剩余 23 个虽然 task ID 未进入该评测，但与当前 SFT 数据共享至少一个训练实体。

这不是重新采样轨迹能够解决的问题。只改变 seed、trial 或用户模拟器回复，仍然是在模型或规则已经间接接触过的业务实体上评测。

## 5. 后续选择

### 方案 A：先冻结 final task，再重建训练集（严格 entity-OOD 可选项）

1. 从尚未用于开发评测的 23 个 official test task 中选择分层 final holdout；
2. 冻结 task ID、任务文本、实体组、上游 commit 和配置哈希；
3. 从未来 SFT/DPO/GRPO 数据中删除与该 holdout 重叠的实体；
4. 从相同 Base checkpoint 重新训练最终对比模型；
5. 在训练、Reward 和阈值全部冻结后才运行 final holdout。

代价是现有 SFT v1/v2 只能继续作为开发 checkpoint，且重建数据后需要重新训练。优点是最终结论最干净。

### 方案 B：构造全新实体与任务

扩展 Retail 数据库并构造新用户、订单、商品和任务，可以获得真正的实体隔离集；但需要重新验证环境、reference actions、Policy 和 evaluator，工程量和人工审计成本更高。

### 方案 C：使用剩余 23 个 task（当前采用）

将全部 23 个未参与开发评测、task ID 未进入 SFT 的任务封存为项目内部 task-heldout 最终测试。它可以检验新任务目标上的迁移，但不能支持 entity-unseen、tau2 官方榜单或生产业务泛化结论。

## 8. 对抗式审阅

1. task ID 没见过不等于业务实体没见过；
2. entity-disjoint 仍不能完全消除相同任务模板带来的分布相似性；
3. 删除实体重叠训练行可能显著缩小当前 40 行 TRAIN，需要先计算数据损失；
4. 若先看候选任务上的模型结果再选择 holdout，会产生选择偏差；候选筛选只能使用任务定义、能力类别和实体关系，不能使用模型 reward；
5. 外部用户模拟器即使 temperature 0 仍有后端非确定性，最终评测仍需多 trial 并保留原始轨迹。
6. 当前 checkpoint 曾使用部分 official test task 做开发或训练，因此即使剩余 23 个 task 未见过，也不能将其包装成完整 official test split 的无污染 leaderboard 结果。
