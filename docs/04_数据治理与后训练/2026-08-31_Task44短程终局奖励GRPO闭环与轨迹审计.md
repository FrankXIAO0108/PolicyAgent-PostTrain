
## 3. Task 44 的实际目标

用户要求在 pending 订单 `#W9300146` 中，将当前 Desk Lamp 替换为最便宜的可用变体，并把差价退回礼品卡。

目标终态：

- 原 item `9190635437` 替换为 `5320792178`；
- 新商品价格 `$135.24`；
- `$17.99` 退回 `gift_card_7245904`；
- 礼品卡余额 `$17.00 -> $34.99`；
- 订单状态变为 `pending (item modified)`。

写操作前还需要确认订单、旧/新商品、退款方式和本次修改范围。Task 44 的 gold action 与 Policy 对礼品卡余额的文字存在歧义：gold 要求使用该礼品卡，而 Policy 的余额条件未明确区分补款与退款。因此本轮 terminal-positive 不能自动等同于独立确认的 policy-compliant GOLD。

## 4. 本轮终局 Reward 的真实语义

代码实际执行的是：

```text
reward = 1
iff
tau2 final environment state == gold state
and user_stopped == true
```

它不是单独的 DB match。以下内容均不进入 scalar Reward：

- 写前确认质量；
- 工具路径效率；
- 最终回复事实一致性；
- Policy Guard；
- communication evaluator；
- required action recall。

因此配置中的 `terminal_reward_is_db_state_only=true` 只是说明 Reward 的业务正确性来源是终态 DB，不应理解为“DB 一旦正确就必得 1”。当前 post-GRPO candidate 1 的 DB 已正确，但没有正常结束对话，所以 scalar Reward 仍为 0。

## 5. GRPO 参数更新证据

- GPU：RTX 4090 24GB；BF16 LoRA，未量化。
- `max_steps=2`，`num_generations=4`，共 2 组、8 条 rollout。
- `learning_rate=5e-6`，`beta=0.02`，`loss_type=dr_grpo`。
- 两组 Reward：`[1,0,0,1]`、`[0,0,1,0]`。
- mixed group：2/2；零标准差组：0/2。
- optimizer step：2/2；非零梯度 step：2/2。
- `grad_norm`：`0.0491968 -> 0.0350054`。
- KL：`0 -> 0.000414496`；KL 路径存在且第二步非零，但样本不足以评价约束强度。
- entropy：`0.163377 -> 0.162764`；只能记录，不能据两点判断 entropy collapse。
- train loss：`0.0221670`；运行时间 `493.8852 s`。
- 起始与最终 adapter 权重 hash 不同；504 个 LoRA tensor、33,030,144 个可训练参数均为有限值。
- optimization evidence：`PASSED`，全部约束项为 true。
- 训练审计警告：`HIGH_COMPLETION_CLIPPING`，平均 clipped ratio `0.125`，最大 `0.25`。

结论：真实的 rollout、组内相对优势、反向传播、LoRA 参数更新、adapter 保存与模型合并链路成立。该结论不等于行为提升成立。

### 7.3 Action matcher 限制

多条轨迹实际调用 `calculate("153.23 - 135.24")` 并得到正确 `$17.99`，但 action matcher 仍把 calculate 标为 unmatched，因为 benchmark action 的表达式方向不同。该 `action recall=0.8` 不能用来断言模型没有计算；本轮它不参与 Reward。

## 8. 对本轮结果的判定

### 已成立

1. Qwen3-4B 在真实 tau2 Retail 环境中完成了 2-step、n=4 的 GRPO 参数更新。
2. 两个训练 group 均有非零 Reward 方差，两步均产生有限非零梯度。
3. adapter 权重发生变化，模型成功合并，GRPO merged checkpoint 可独立加载和采样。
4. 同协议 post-GRPO 轨迹已生成并完成逐条审计。
5. 观察到一个真实成功翻转，以及部分成功轨迹的事实表述改善。

### 未成立

1. 端到端 scalar terminal success 没有提升：仍为 `3/4`。
2. post-GRPO 采样审计状态为 `REJECTED`，原因是一条轨迹被 completion budget 右删失。
3. 不能声称 GRPO 获得跨任务泛化、稳定业务提升或统计显著提升。
4. 不能声称 terminal-positive 轨迹全部 policy-compliant 或过程高质量。
5. 不能把成功轨迹平均工具数 `8.33 -> 6.33` 单独包装成效率提升；样本过少且同时出现 20-call 长尾。

项目状态应表述为：**GRPO 工程闭环已完成，行为提升证据不足；Reward 与长轨迹停止控制暴露出可定位的下一轮问题。**

## 9. 下一步审计门槛

下一步不应直接增加训练步数。

1. 将 Task 44 的失败拆为两个独立标签：
   - `DB_STATE_FAILURE`：没有完成正确写入；
   - `POST_WRITE_COMPLETION_FAILURE`：写入正确但没有完成最终回复和用户停止。
2. 离线验证分层 Reward 是否能同时做到：
   - 保留 GRPO-0/2/3 的高分；
   - 将 GRPO-1 的正确写入与冗余/未完成区分开；
   - 不把未写入的 SFT-2 当作成功；
   - 对事实冲突、确认缺失、冗余读取提供独立、可解释的过程信号。
3. 若要验证 4096 是否只是评测右删失，应让 SFT 与 GRPO **同时**在同一 6144 预算下重跑，明确标注为 post-hoc censoring sensitivity，不替换本轮冻结结果。
4. 在任何业务提升声明前，必须换到未参与 SFT/GRPO 的冻结任务做 holdout 评测。

## 10. 最终结论

Task 44 达成了用户当前最需要的第一层目标：真实 GRPO 训练与前后评测工程闭环已经跑通。它没有给出干净的指标提升，而是给出了更有解释力的结果：模型的正确写入覆盖增加，但长尾轨迹因重复工具调用和停止控制失败抵消了端到端收益。

纯终局 Reward 能训练“最终是否做成”，但无法独立教会模型“如何用更短、更事实一致、更合规的路径做成”。这构成下一轮分层 Reward 对照实验的直接证据，而不是根据预设结论引入复杂 Reward。
