# SFT 残余失败审计与后训练分流

日期：2026-08-23

状态：开发级轨迹审计；未启动新训练，未修改 Reward

结论边界：本报告基于冻结的 18 任务 × 4 trials Base / SFT v1 / SFT v2 产物。分类是工程诊断，不是独立业务专家金标，也不构成正式 RL 启动批准。

## 1. 审计目的

SFT v1 与 SFT v2 的聚合成功率均为 `48/72`，但任务级翻转和过程指标明显不同。本报告不再用单一成功率回答“模型是否变好”，而是逐项回答：

1. 失败是缺少正确示范、错误偏好，还是长程执行稳定性问题；
2. 当前是否存在同一 checkpoint 内可比较的成功/失败 rollout；
3. 下一步应继续 SFT、构造局部 DPO 偏好，还是进入 Agentic GRPO；
4. 候选 Reward 能否由程序稳定计算，以及是否可能误罚成功流程。

审计对象包括三类关键任务：

- 三模型均未稳定成功：19、39、74（其中 19、74 均为 0/4；39 为 1/4、0/4、0/4）；
- SFT v2 相对 v1 明显回退：40、77、100；
- SFT v2 新出现的终止失败：50。

## 3. 分流结论

| Task | Base / v1 / v2 成功 trial | 主要失败 | 当前优先路线 | 理由 |
|---:|---:|---|---|---|
| 19 | 0 / 0 / 0 | 多目标比较、错误合并操作、金额沟通、完成后继续操作 | SFT + 确定性校验 | 当前 checkpoint 没有正 rollout；正确流程和金额都能明确写出 |
| 39 | 1 / 0 / 0 | 身份恢复不稳、最便宜变体比较错误、最终答案错误 | SFT + argmin/答案校验 | SFT 内无正 rollout；问题主要是比较与事实绑定，不是探索 |
| 40 | 2 / 4 / 2 | 错误拒绝可用支付修改，或执行无关取消 | 局部 DPO 候选；随后再评估 GRPO | v2 内有 2 正 2 负，关键决策点明确，且正轨迹可以程序验证 |
| 50 | 4 / 4 / 3 | 未转人工、虚构可下新单、与用户模拟器形成文字死循环 | 终止/转人工 SFT + DPO 候选 | v2 有正负差异，但 benchmark 的部分 reward=1 轨迹并非理想过程，须先复核 chosen |
| 74 | 0 / 0 / 0 | 完成取消但漏掉笔记本修改；误解 pending modification 和 variant 可用性 | SFT | 全部 rollout 无完整成功，当前不具备 GRPO 组内学习信号 |
| 77 | 4 / 4 / 3 | 54 次相同、无状态变化的读取，最终 `max_steps` | GRPO 首选候选 | 同一 checkpoint 有 3 条干净成功与 1 条明确循环失败；信号稳定且可程序化 |
| 100 | 3 / 2 / 0 | 错变体、漏子任务、错误 Policy 拒绝 | SFT + 局部偏好数据 | v2 无成功 rollout；现阶段 GRPO 组内全零，无法形成有效相对优势 |

该表不表示“某个任务永久只用一种算法”。分流针对的是当前证据下的首个修复动作。例如 task 40 可以先用局部 DPO 固化支付方式决策，再用环境 Reward 检查错误写操作；task 77 在进入 GRPO 前仍需要一条明确的正确终止示范作为 SFT 基线。

## 4. 逐任务根因

### 4.1 Task 19：反事实比较和多目标决策

任务要求比较两个方案：退水瓶可退款 `$54.04`；将宠物床和办公椅换成最低价版本共节省 `$41.64`。因为用户明确规定只能完成一类操作时选择更省钱方案，reference 最终只要求退水瓶，并告知两组金额。

SFT v2 trial 0 的 DB 与 7/7 reference actions 均匹配，但完成退货后又尝试额外换货、重复退货，产生两次工具错误；最终还漏报两个关键金额，所以 reward 为 0。trial 1 则把水瓶、宠物床和办公椅合并为一次 exchange，既改变了用户明确要求的 return，也没有给出 `$41.64` 的独立比较结论。

这不是单纯“少调用工具”问题，而是：

1. 将用户条件转成互斥方案；
2. 计算各方案收益；
3. 选择方案后停止；
4. 把计算依据写入最终回复。

当前 v2 四次均失败，不能直接做 GRPO。优先补同类“比较两个可执行方案后择一”的高质量 SFT，并加入金额和互斥动作校验。

### 4.2 Task 39：正确写状态但最终比较答案错误

SFT v2 trial 2 成功把地址更新为 Phoenix，`db_match=true`，但只检查了一个 T-shirt 商品后声称最低价为 `$46.85`；真实最低价是 `$46.66`。因此这是典型的 partial success：状态写入正确，比较选择和最终自然语言错误。

另外三个 v2 trials 均因身份查找反复报错而 `too_many_errors`。所以 task 39 实际包含两类问题，不能压成一个负样本：

- 身份恢复策略：新旧邮编查找失败后如何切换证据；
- 商品变体 argmin：必须枚举可用候选再做确定性最小值比较。

若 Reward 只看 DB，会把 trial 2 错误地当高分。进入 RL 前必须把“最终答案中的价格是否等于工具证据中的可用最小值”纳入独立校验。

### 4.3 Task 40：已学会的支付修改发生回退

SFT v1 为 4/4。SFT v2 trial 1、2 使用四步干净流程：鉴权、用户查询、订单查询、`modify_pending_order_payment(..., credit_card_8897086)`，均成功。

两个失败 trial 的错误不同：

- trial 0 正确回答礼品卡余额和原 Mastercard，但错误声称 pending order 不能修改支付方式，漏掉写操作；
- trial 3 在无取消意图时调用 `cancel_pending_order(..., ordered by mistake)`，造成错误终态。

该任务存在同 checkpoint、同协议下的干净正负轨迹，是构造局部 chosen/rejected 决策对的强候选。chosen 应优先使用 v2 trial 1/2，而不是 v1 trial 0：后者先尝试余额不足的 gift card 并产生一次可避免的工具错误，虽然最终 benchmark 成功，但过程不是最佳。

### 4.4 Task 50：工具统计漏掉的自然语言死循环

目标行为是不能恢复已取消订单，在用户持续施压时转人工。SFT v2 trial 0 只调用 3 个查询工具，但之后反复声称可以帮助下新订单、要求用户选择系统并不存在的运输方式；用户模拟器也重复要求选择最快配送，双方循环至 `max_steps`。

这是重要的新诊断：`mean_repeated_exact_calls` 看不到无工具对话循环。后续过程分析至少要增加：

- 连续或高相似 assistant 文本重复；
- 连续或高相似 user 文本重复；
- 在能力边界已确定后仍继续询问不可满足参数；
- 应终止或转人工却到达 `max_steps`。

v2 trial 2 包含明确 `transfer_to_human_agents`，可作为候选正轨迹；trial 3 虽然也转人工，但在转人工前进行了多次不必要商品查询。trial 1 获得 reward=1，却没有调用 reference 中的转人工工具，因此不能仅凭 benchmark reward 自动选为 chosen。

### 4.5 Task 74：多订单、多目标和产品变体绑定

正确终态同时要求：

1. 取消五件商品的 pending order `#W3189752`；
2. 将另一个 pending order `#W5166363` 中的笔记本 `3334537816` 修改为 i9 / 256GB / silver 的 `3265035808`。

SFT v2 trial 1 正确取消第一笔订单，却把旧 item 的 `available=false` 错误解释为 pending item 不可修改，并声称不存在符合条件的新 variant，最终漏掉第二个写操作。trial 2 在一次工具错误后进入 assistant/user 文字重复，最终 `max_steps`；其余 v2 轨迹也没有完整成功。

该问题首先是状态语义和属性约束绑定，不是缺少惩罚。当前所有模型均 0/4，说明需要增加跨订单双目标、pending modification 与 variant 选择的正示范；在出现可重复成功 rollout 前不进入 GRPO。

### 4.6 Task 77：最干净的 Agentic GRPO 候选

SFT v2 trial 0、1、3 都执行同一五步成功流程：鉴权、用户查询、订单查询、产品查询、换成最大容量 `3399869890`。

trial 2 在用户明确选择 100ml 后，没有调用 `get_product_details` 获取变体，而是对当前 30ml item 连续调用 `get_item_details(item_id=5081446110)` 54 次：

- 57 次工具调用；
- 53 次完全重复调用；
- 0 次写操作；
- 0 次工具错误；
- 最终 `max_steps`。

这是当前最适合程序 Reward 的失败：相同参数、相同返回、环境无变化，继续调用没有任何信息增益。可以在不依赖 LLM Judge 的情况下扣分，同时用三个成功 trial 验证该规则不误罚正常产品查询。

### 4.7 Task 100：SFT v2 的真实语义回退

正确动作同时要求：

- pending order `#W3295833` 中，将行李箱和滑板改成精确 variant `7160999700`、`6956751343`；
- delivered order `#W8488728` 中退回登山靴 `5676696062`。

SFT v1 trial 1 可完整执行两笔写操作。SFT v2 trial 1 虽执行两类操作，但选择了错误 variant `9956648681`、`9594745976`；trial 2 只退登山靴，并错误声称 Policy 不允许修改 pending order。v2 四个 trials 都只匹配 1/2 reference actions，`db_match=false`。

该任务不是工具格式问题，而是精确多属性约束、两个订单实体和两个子目标的联合保持问题。v2 没有成功组内样本，直接做 GRPO 很可能得到组内全零或只奖励部分成功。优先补同结构但实体隔离的多目标正示范，并为“全部子目标完成”设置门禁。

## 5. Reward 候选与正向验证要求

新增的对话重复诊断得到：

| 指标（72 trials） | Base | SFT v1 | SFT v2 |
|---|---:|---:|---:|
| 平均完全重复 Assistant 文本 | 0.74 | 0.00 | 1.46 |
| 平均完全重复 User 文本 | 0.69 | 0.00 | 1.36 |
| 到达 `max_steps` | 1 | 0 | 3 |
| `max_steps` 且同角色文本连续重复至少 3 次 | 1 | 0 | 2 |

逐例核验表明：Base 的候选是 task 39 trial 3；SFT v2 的候选是 task 50 trial 0 和 task 74 trial 2。task 77 trial 2 虽然也到达 `max_steps`，但它是 54 次同工具连续调用，不是文字重复。这证明工具循环和对话循环需要分开建模，不能共用一个“重复次数”字段。

候选过程信号按可靠性分层：

### 5.1 可直接离线验证的强信号

- `max_steps` 或 `too_many_errors`；
- 同一工具、同一参数、同一返回且中间无状态变化的连续重复；
- 非用户目标中的写操作，例如 task 40 的错误取消；
- reference 或任务规格要求的多个子目标只完成一部分；
- 工具返回失败后不改变参数、不改变计划的重复调用。

### 5.2 必须增加校验器后才能使用的信号

- 价格最小值、最大容量等集合比较；
- 最终回复金额与工具证据绑定；
- 多属性 variant 精确匹配；
- pending / delivered / cancelled 状态所对应的动作能力；
- 应转人工的终止边界。

### 5.3 当前不宜作为标量 Reward 的信号

- 未经独立裁决的 Policy Grounding V2.2 标签；
- 外部 DeepSeek NL Judge 的即时分数；
- 单纯“工具调用越少越好”；
- 单纯 `reward==1`，因为 task 50 已出现 reward 成功但未执行理想转人工流程；
- 单纯 `db_match=true`，因为 task 39 已出现状态正确但最终答案错误。

任何新 Reward 在进入训练前，必须先回放到：

1. task 40 v2 trial 1/2 的干净支付修改；
2. task 50 v2 trial 2 的转人工流程；
3. task 77 v2 trial 0/1/3 的五步成功流程；
4. 既有《过程 Reward 离线正向验证报告》中的 24 条共同成功轨迹。

目标不是只让失败轨迹降分，而是证明成功轨迹不会因必要查询、合法恢复或正确终止被误罚。

## 6. 下一阶段门禁

### P0：不需要 GPU

1. 已完成：为评测卡增加自然语言重复和终止边界诊断，覆盖 task 50，并额外发现 task 74 trial 2；
2. 为 task 39/74/100 定义可程序检查的集合比较、variant 和多子目标完成规格；
3. 将 task 40/50/77 的候选正负轨迹生成所有者复核证据包；
4. 对候选 Reward 做成功流程正向验证和失败流程排序验证。

### P1：仍优先 SFT / DPO

1. 从训练域另取实体隔离的同构任务，补充 19/39/74/100 的正示范；
2. 只在关键分叉点构造 task 40/50 类 chosen/rejected，不直接把当前回归任务回灌训练；
3. 训练后必须启用新的未参与 Reward 设计和数据构造的 holdout。

### P2：条件式小规模 GRPO

只有同时满足以下条件才启动：

1. 每个训练任务的 rollout group 内存在非恒定 Reward；
2. task 77 类循环失败能被稳定降分；
3. 成功流程误罚率通过开发级人工复核；
4. final-answer、variant 与多子目标信号不再是 Reward 盲区；
5. RL 训练任务与最终 holdout 严格分离并记录实体、任务和配置哈希。

## 7. 对抗式审阅

1. **“v2 同任务有正负轨迹，所以一定适合 RL”不成立。** task 50 的 reward=1 轨迹中存在未转人工的非理想过程，chosen 必须额外复核。
2. **“重复调用一定错误”不成立。** 状态改变后的相同读取可能是合法验证；只有参数、返回和中间状态均不变时，才能作为强负信号。
3. **“v2 回退由六条新增数据导致”未被证明。** v2 增加了训练行但保持 80 steps，单样本平均曝光下降；只有一个 checkpoint，不能做因果归因。
4. **“给 task 19/39/74/100 更强惩罚即可解决”不成立。** 当前 checkpoint 缺少稳定成功探索，Reward 无法凭空提供正确 variant、比较结果或完整计划。
5. **当前 18 个任务已经用于开发分析。** 后续若据此设计 Reward 或训练数据，它们只能继续作为 discovery/regression，不得作为最终无污染效果集。

## 8. 当前决策

- `SFT_PLATEAU_PROVEN=false`：v2 持平和回退是边际收益下降信号，不是严格平台证明；
- `DPO_DATA_READY=false`：已有候选 pair，但尚未完成 owner review、临界 turn 切分与泄漏门禁；
- `GRPO_REWARD_READY=false`：task 77 提供了强候选信号，但自然语言循环、final answer、variant 和多目标完成仍有缺口；
- `NEW_GPU_RUN_REQUIRED=false`：下一步是本地分析、校验器和证据包工作。
