# Qwen3-4B 工具协议 SFT 实跑报告

## 一、结论

本次在单卡 RTX 4090 上完成了真实的 Qwen3-4B 4-bit QLoRA Tool SFT、adapter
保存、模型 merge 和 Base/SFT 冻结 holdout 对比。隔离式工具协议 warmup 门禁通过，
但正式 Retail 数据门禁、业务提升声明和 Agentic GRPO 门禁均未开放。

Base 的 20 条输出都绕过 `respond_to_user` 或认证工具，直接生成自然语言；这复现了此前

认证任务还能从未见过的消息中精确复制邮箱、姓名和邮编。

## 五、训练曲线解释

第 1、2 步 loss 分别约 2.94 和 3.46，第 5 步降至 0.75；第 80 步约为
`8.6e-5`，最终 token accuracy 为 1，总体 train loss 为 0.1489。这说明模型确实学会了
目标格式，但也说明 80 条模板化数据在 4 epochs 下非常容易被拟合。

因此 100% 不能解释为 Retail 业务成功率达到 100%，也不能证明模型已经会长链路规划、
状态追踪、授权判断或写操作确认。当前证据只支持：模型在独立但同分布的合成 holdout
上学会了三种第一步动作的工具调用协议。

## 六、失败与工程修正

首次云端 preflight 被数据哈希门禁拦截。原因是 Windows `core.autocrlf=true`，构建器
记录了 CRLF 文件哈希，而 Git blob 和 Linux checkout 使用 LF。修复为：

1. 数据构建器使用 `write_bytes` 固定 UTF-8/LF；
2. `.gitattributes` 对该数据目录强制 `eol=lf`；
3. 重新生成 manifest 后，本地和云端 SFT SHA256 均为
   `66BF51899DF17A18601CF19E9753ECB210B88A285D4DD47CBC573F4654A75402`。

这个失败证明哈希门禁有效，避免了训练数据字节已变化却仍声称可复现。

## 七、下一步门禁

下一步只替换起始模型为本次 merge 模型，保持原有 8 个任务、每任务 4 候选、seed、
环境和 reward 不变，执行 32 条无更新 Agent rollout。重点比较：

1. 工具调用率是否从 0/32 提升；
2. action-progress gate 后是否出现非零且有方差的 reward；
3. 是否能正确执行认证后继续读工具，而非只会第一步；
4. 是否出现模板复读、错误参数、无限澄清或 reward shortcut。

只有真实 rollout 产生稳定动作推进和可用组内奖励方差，才允许设计小步 Agentic GRPO。
