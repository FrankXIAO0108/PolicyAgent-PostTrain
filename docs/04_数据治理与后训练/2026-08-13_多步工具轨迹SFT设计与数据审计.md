# 多步工具轨迹 SFT 设计与数据审计

> 日期：2026-08-13  
> 范围：隔离的 Qwen3-4B Tool Agent 工程实验  
> 结论边界：这是开发者构造的合成训练数据，不是 tau2 人工金标，也不支持 Retail 业务提升结论。

## 1. 为什么旧 Tool-SFT 不够

旧版 `retail_tool_protocol_sft_v1` 的每行输入只有一条用户消息，输出只有一个工具调用。它训练的是：

```text
用户句子 -> 第一个工具调用
```

2026-08-13 的 32 条冻结 rollout 证明该训练确实解决了第一层问题：Tool Call 从 Base 的
`0/32` 变成 `32/32`。但其中 `29/32` 仅执行两次工具调用，`32/32` 都没有完成完整交互。
这说明模型尚未学会：

- 读取身份查找结果后继续查询用户；
- 读取用户详情后定位订单；
- 读取订单与商品状态后选择下一步；
- 在写操作前向用户解释并取得确认；
- 读取写操作返回后进行真实、简洁的最终沟通。

所以当前瓶颈不是“是否会输出 `<tool_call>`”，而是“是否会依据工具返回持续决策”。

## 2. 为什么不直接学习失败 rollout

v5 rollout 是诊断证据，不是正向训练金标。多数轨迹在第二步结束，直接作为 SFT 正样本会把
“执行两步后停止”固化到模型中。另一方面，tau2 静态动作序列也不能自动等同于唯一正确轨迹；
项目既有审计已经发现 benchmark label、工具语义和策略之间存在冲突。

因此 v1 多步数据只用于隔离工程验证，来源明确标记为
`developer_authored_synthetic_multistep_trajectory`，且不包含冻结 tau2 task 内容。

## 3. 数据组织：完整轨迹与决策点切片

先构造完整轨迹，再将每个 assistant 工具决策切成独立训练样本：

```text
完整轨迹
  用户请求
  assistant 工具调用
  tool 返回
  assistant 下一工具调用
  tool 返回
  ...

决策点样本
  prompt     = 当前决策之前的全部历史，包含 assistant tool_call 与 tool result
  completion = 当前唯一正确的下一次 assistant tool_call
```

这种设计保留了多步上下文，同时继续使用 `completion_only_loss=True`。模型只对下一步 assistant
动作计算损失，不会被要求“生成”用户文本或工具返回。

当前数据覆盖三类轨迹：

1. 查询订单状态；
2. 修改 pending 订单商品；
3. 退回 delivered 订单商品。

训练侧共有 24 条完整轨迹、136 个决策点；留出侧共有 6 条完整轨迹、34 个决策点。
训练与留出使用不同的邮箱、用户、订单、商品和支付 ID。

## 4. 质量门

构建器 `src/training/retail_multistep_tool_sft_data.py` 自动检查：

- 训练与留出 trajectory ID 不相交；
- 每个 scenario ID 唯一；
- 每个 assistant tool-call ID 与紧随的 tool-result ID 一致；
- 数据中实际存在读取一个或多个 tool result 后的决策点；
- 所有状态写操作前都绑定 `respond_to_user` 的明确肯定回复；
- 所有行均禁止人工金标与业务效果声明；
- 四个 JSONL 文件均由 manifest 记录行数和 SHA-256，包括源轨迹和派生决策点。

这仍不是语义正确性的完整保证。合成数据在正式训练前仍需抽样人工审查；正式 Retail 数据门则仍需
独立双人盲审与冲突裁决。

## 5. 训练和评测

配置：`configs/retail_multistep_tool_sft_qwen3_4b_v1.json`  
入口：`scripts/run_retail_multistep_tool_sft.sh`

起始模型固定为已完成的 Qwen3-4B 单步 Tool-SFT merged checkpoint。计划使用 4-bit NF4 QLoRA、
136 steps、学习率 `5e-5`、单卡 RTX 4090。先执行：

```bash
bash scripts/run_retail_multistep_tool_sft.sh preflight
```

预检通过后才允许训练：

```bash
bash scripts/run_retail_multistep_tool_sft.sh train
```

留出评测除总体指标外，新增三组指标：

- `first_decision`：无工具返回时的首步决策；
- `post_tool_decisions`：至少读取一次工具返回后的继续决策；
- `confirmed_write_decisions`：用户明确确认后的写操作决策。

真正对应当前根因的是后两组。即使总体 Tool Match 很高，只要 post-tool 或 confirmed-write 指标差，
就不能认为多步能力已经建立。

## 6. 后续判定

多步 SFT 完成后，需要在同一冻结的 8-task 多轮协议下比较旧 Tool-SFT 与新 Multi-step Tool-SFT：

- 每条轨迹工具调用数；
- required action recall；
- 完成率与 unfinished 比例；
- 工具错误、重复调用、未确认写操作；
- 同任务多采样的 reward/action 方差。

只有多步 SFT 仍留下稳定、可验证且具有组内差异的系统性失败，并且 reward 能区分好坏轨迹时，
才有理由启动 GRPO 权重更新。多步 SFT 工程实验不会自动打开正式 Retail 后训练数据门。
