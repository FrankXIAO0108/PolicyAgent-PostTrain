日期：2026-08-21

## 0. 结论

本次没有新增 Reward 权重，也没有启动训练，而是把已经实现的 Agentic GRPO v1 Reward
离线回放到 seed19/seed20 的两组 30-task 冻结 SFT 轨迹上，验证：

1. 8 个成功/失败翻转对中，成功轨迹是否得到更高分；
2. 12 个双方共同成功任务、24 条成功轨迹是否被过程规则误罚；
3. Tool error 后恢复成功的轨迹是否仍能保留正向信用；
4. 原始 Reward 是否存在可以由成功流程暴露的 verifier 假阳性。

审计首先发现 task108 的严重假阳性：Agent 正确返回同一组三件商品，只是 `item_ids`
顺序与 reference action 不同，DB 和最终回复均正确，原 Reward 却把 action recall 判为 0，
成功轨迹只得 0.05。修复无序 item 集合比较后：

- 共同成功轨迹 proxy score 均值：`0.9871`；
- 共同成功轨迹最低分：`0.90`；
- 8 个翻转对中成功轨迹得分更高：`7/8`；
- 剩余 task67 成功/失败均为 `0.90`，因为二者 DB、动作和 Tool error 完全相同，
  只有最终自然语言答案不同，而 v1 Reward 明确没有使用 NL assertion。

因此，正向验证确实修复了一个真实 Reward 假阳性，但也证明当前 v1 Reward 无法覆盖
`final-answer grounding`。随后新增的 claim-state consistency 诊断可以核验显式绑定的订单号、
状态和单笔付款金额，并把 task67 的成功轨迹判为 `PASS`、失败轨迹路由为 `REVIEW`；但该
诊断尚未进入标量 Reward。`ready_to_use_v1_reward_for_grpo=false` 保持关闭。

## 2. 正向验证发现的假阳性：task108

期望写操作：

```json
{
  "item_ids": ["9612497925", "7127170374", "6268080249"]
}
```

两个成功 Agent 实际写操作：

```json
{
  "item_ids": ["6268080249", "7127170374", "9612497925"]
}
```

三件商品完全相同，返回操作的业务语义不依赖列表顺序。两个 Agent 都得到：

- Tau2 reward = 1；
- DB match = true；
- 正确退款总额和最终回复。

原 `compare_with_tool_call` 按 list 顺序严格比较，导致：

- required action recall = 0；
- 正确写操作被计为 unexpected write；
- environment-state × action-progress 门禁把 DB 成功从 1 压成 0；
- 最终 Reward proxy = 0.05。

这是 Reward verifier 的错误，不是模型错误。

### 2.1 最小修复

`one_to_one_action_progress` 现在只对明确无序的 Retail 参数规范化：

- 仅有 `item_ids`：按集合顺序规范化；
- 同时有 `item_ids/new_item_ids`：把旧物品与新物品组成 pair 后排序；
- 如果旧新映射改变，即使两个 list 包含相同元素，也不会误判为匹配；
- 其他 list 参数保持原语义，不做广泛排序。

修复后 task108 的 action recall 恢复为 1，unexpected write 恢复为 0。

## 5. task67 暴露的剩余缺口

task67 两条轨迹：

- 工具序列完全相同；
- 两次错误邮编尝试完全相同；
- DB 均为 true；
- required action recall 均为 1；
- Tool error 均为 2。

失败轨迹把错误订单当作“最近订单”，回答 `$919.67`；成功轨迹回答正确的 `$829.43`。
Tau2 NL assertion 可以区分二者，但 Agentic GRPO v1 为避免把外部 LLM Judge 直接放进训练环，
明确设置 `nl_assertions_used=false`，所以两条轨迹均得 0.90。

这里不能简单把 DeepSeek/Qwen Judge 分数直接加入 GRPO，原因是：

1. Judge 非确定性会增加组内 reward 噪声；
2. 每个 rollout 调用 Judge 会显著增加成本和延迟；
3. 模型可能针对 Judge 表达偏好进行 reward hacking；
4. 当前 final-answer correctness 还没有独立 holdout 校准。

### 5.1 程序化 claim-state consistency 结果

本轮已复用并扩展 `src/training/teacher_evidence_pack.py` 中的证据包检查器：

- 从成功 Tool observation 或最终状态提取订单状态；
- 仅在付款历史中恰好存在一笔 `payment` 时提取金额，避免错误合并退款/换货交易；
- 只核验同一局部文本段内显式绑定的“订单号—金额”和“订单号—状态”；
- 金额与事实冲突标记为 `CONTRADICTED/FAIL`；
- “最新/最近订单是 X”这类比较选择不做伪推断，标记为 `UNVERIFIED/REVIEW`；
- 不读取 Tau2 隐藏 reference action 或 NL assertion。

task67 的 Tool 返回没有下单日期。失败轨迹虽然正确复述了三个订单各自的金额，却断言
`#W3445693` 是最近订单；新诊断将该断言路由为 `REVIEW`。成功轨迹最后明确说明缺少日期，
并正确绑定 `#W6729841 -> $829.43`，诊断为 `PASS`。因此诊断层可以区分该 pair，但不能据此
声称已经程序化证明“#W6729841 最晚下单”；正确目标仍来自 benchmark 金标。

冻结 60 条轨迹上的诊断结果：

- 32 条 Tau2 成功轨迹中，claim-state `FAIL=0`；
- 8 个 flip 中只有 3 个双方都落在该 checker 的可评价范围；
- 可评价 flip 中成功轨迹被优先的只有 task67；
- 其余任务的 `NOT_APPLICABLE/REVIEW` 不得当成通过，也不能用于计算泛化准确率。

这一步补上了高精度事实核验与保守路由，但没有解决一般语义目标选择。无法程序化核验的开放式
NL assertion 应留在离线 Judge 或最终评测中，而不是未经校准直接进入在线 GRPO Reward。

## 6. 停止条件离线诊断

本轮继续验证了一个不依赖 LLM Judge 的过程信号：Agent 是否在显式终止后停止，以及成功
人工转接是否按 Retail policy 完成规定序列。规则只检查可机械判定的事实：

- `###STOP###`、`###TRANSFER###`、`###OUT-OF-SCOPE###` 之后不得继续产生消息或工具调用；
- `transfer_to_human_agents` 必须有明确的 `Transfer successful` Tool Result；
- 成功转接后不得再调用工具；
- 成功转接后必须发送规定的转接提示，并由用户模拟器返回 `###TRANSFER###`；
- `too_many_errors` 等没有显式终止标记的异常结束单列为失败。

该规则不根据最终回复推断“业务任务是否已经完成”，也不读取隐藏 reference action，避免把
开放式完成判断伪装成确定性信号。

冻结 60 条轨迹上的结果：

| 指标 | 结果 |
| --- | ---: |
| PASS | 59 |
| REVIEW | 0 |
| FAIL | 1 |
| 正常 `user_stop` | 59 |
| `too_many_errors` | 1 |
| 成功人工转接且序列完整 | 3 |
| 成功轨迹上的停止条件 FAIL | 0 |

唯一 FAIL 为 `task107/run_b`：轨迹因 `too_many_errors` 结束，没有任何显式终止标记。这个
结果与既有未完成交互扣分方向一致，不是一个新的独立失败样本。三条真实人工转接轨迹的
序列均正确，因此现有数据没有覆盖“转接后继续调用工具”的真实负例。

反事实单测覆盖了：停止标记后继续活动、成功转接但缺少固定提示、缺少转接终止标记、缺失
Tool Result 不能被假定为成功。后者被路由为 `REVIEW`，而不是误判为 PASS 或 FAIL。

结论边界：这证明了规则实现和真实成功轨迹兼容，但不能估计违规召回率，也不足以单独形成
新的 Reward 权重。停止条件继续保留为离线诊断；正式接入 Reward 仍需包含真实或独立构造
负例的冻结 holdout。

## 7. Tool error 分层与恢复诊断

v1 Reward 对每次 Tool error 统一扣 `0.05`，最多扣 `0.20`。冻结 60 条轨迹共有 31 次错误：

| 可观察错误类别 | 全部轨迹 | 成功轨迹 |
| --- | ---: | ---: |
| `AUTH_LOOKUP_MISS` | 13 | 2 |
| `READ_TOOL_ERROR` | 3 | 0 |
| `WRITE_TOOL_ERROR` | 15 | 4 |

这里的类别只描述工具类型和返回结果，不推断责任归属。`AUTH_LOOKUP_MISS` 特指
`find_user_id_by_email/name_zip` 返回 `Error: User not found`；它是无状态副作用的查询未命中，
但仍可能来自用户错误输入或 Agent 编造参数，不能自动等价为“合理探索”。

task67 提供了一个可核实的误罚案例：用户先后给出邮编 `98178`、`98186`，两次查询均未命中；
用户第三次改为 `98187` 后查询成功。Agent 每次使用的都是用户当轮明确提供的值，因此前两次
错误不是 Agent 无视已有事实或违反业务前置条件。成功轨迹仍被统一 Tool error penalty 扣掉
`0.10`。

为检查这是否影响 Reward 区分能力，v12 只做反事实重算：保留原始分数不变，另算“不对
`AUTH_LOOKUP_MISS` 扣分”的分数。结果是：

- task67 成功轨迹：`0.90 -> 1.00`；
- task67 失败轨迹：`0.90 -> 1.00`；
- 8 个 flip 中成功轨迹排序更高仍为 `7/8`；
- 未解决的仍是 task67，且仍然并列。

因此有两个同时成立的结论：统一 Tool error 扣分缺少错误来源区分；但只豁免身份查询未命中
不会改善成功/失败排序，也不能解决 final-answer grounding。当前不修改线上 Reward。若未来
要做 class-aware penalty，至少还需验证调用参数是否来自最近用户输入、错误后是否向用户澄清、
以及后续成功是否真正依赖新信息。

## 8. 多实体写操作与联合约束审计

冻结轨迹中共有 13 条轨迹包含多物品写操作，共 22 次调用：

| 指标 | 结果 |
| --- | ---: |
| 最终成功轨迹 | 4 |
| 最终失败轨迹 | 9 |
| Tool Result 成功 | 10 |
| Tool Result 报错 | 12 |

这组数据否定了“多物品 Tool 成功即可作为正奖励”：Tool 成功同时出现在最终成功与失败轨迹，
而 task100、107 的最终成功轨迹也包含先失败再恢复的多物品写调用。

审计还发现 task105/run_a 两件相同 Tea Kettle 共用同一 `item_id`，因此调用中
`item_ids=[7292993796, 7292993796]` 是数量 2 的合法表示；Tool Result 也保留了两件商品。
若增加“item_ids 必须唯一”的通用规则，会把真实数量语义误判为重复调用。

当前可安全保留的信号已经存在：

- Tau2 工具负责业务前置条件与参数合法性；
- DB reward 检查持久状态；
- one-to-one action progress 检查必要动作覆盖；
- `item_ids/new_item_ids` 作为位置配对比较，允许 pair 顺序变化但不允许 old→new 映射变化；
- one-shot mutation 与重复失败已有 Guard/penalty。

因此本轮不新增多实体 Reward。真正缺失的是“用户要求的所有实体是否都被正确绑定”，这需要
用户意图来源或独立任务金标；仅从调用参数和 Tool Result 无法可靠判断，多加规则会重复计分
或引入假阳性。

## 9. 写前确认联合约束

原确认诊断会在每次写操作后清空确认状态，导致一次明确批量确认只能覆盖第一笔写。冻结轨迹
初扫因此把 74 次写操作中的 26 次判为缺确认，其中 9 次落在最终成功轨迹上。

状态机修正后：确认可以覆盖没有新用户消息插入的连续写操作；一旦用户再次发言，授权立即
失效；同一确认下的后续订单必须出现在确认文本中。修正结果：

| 指标 | 原诊断 | 修正后 |
| --- | ---: | ---: |
| 写操作总数 | 74 | 74 |
| 确认通过 | 48 | 59 |
| 缺确认 | 26 | 15 |
| 成功轨迹上的缺确认 | 9 | 4 |

剩余成功轨迹上的 4 次缺确认来自：

- task66/run_b：2 次。Agent 未先列出动作细节并询问确认，就尝试退货和取消；
- task100/run_a：1 次。Agent 在最终交换参数确定后没有重新列出完整动作并取得明确确认。
- task107/run_a：1 次。完全相同的失败写调用被重复执行，不能继承第一次确认。

这证明 Tau2 outcome success 不等于 policy-compliant process。确认诊断是当前最有希望的过程
约束之一，但仍只检查“确认时序、批次范围和订单绑定”，尚未可靠绑定 item、new item、付款
方式和原因。因此它继续作为离线 Policy 诊断，`confirmation_signal_used_as_reward=false`
保持不变；需要冻结的参数绑定 holdout 后才能讨论 penalty。
