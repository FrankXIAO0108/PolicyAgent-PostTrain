# 退款执行与告知：针对性 GRPO 实验设计 v1

日期：2026-09-07。状态：**设计草案，未冻结、未实现、未获云端执行授权**。

本轮只新增本文，不修改训练代码、Reward、旧实验配置或冻结数据。
本设计不承诺产生正收益；它规定什么结果值得训练、什么结果才算改善。

## 1. 唯一研究问题

从已选出的同一个 SFT checkpoint 出发，针对性 GRPO 能否提高：

> 在正确、合规完成取消订单后，依据实际订单与支付状态，完整且准确告知退款结果的比例？

保持完整 Agent 流程：认证 → 查询订单 → 明确取消范围和原因 → 获得确认 → 取消订单 → 告知退款 → 正常结束。

本轮研究的是**完整工具流程中的退款状态绑定与告知可靠性**，不是通用长程规划能力，也不是证明 GRPO 优于补充 SFT。
只跑一个针对性 GRPO 训练臂，与未继续训练的 SFT 对照。暂不增加 Terminal/Staged 双训练臂、模型规模或 RL 算法对照。

## 2. 选题依据：当前能确认什么

本轮读取本地原始结果，并用当前 `refund_timing_by_payment_v2` 做只读复算：

| 旧 Task113 SFT 随机采样，单一实例 | 实际计数 | 含义 |
|---|---:|---|
| 完整采样 | 32 | 8 个 n=4 组，不是 32 个不同任务 |
| 原口径 terminal_success | 30/32，93.75% | 业务流程已有较高成功基础，不代表完整合规 |
| 退款 v2 诊断 PASS | 24/32 | 仅未检测到其覆盖的立即退款冲突 |

| 退款 v2 诊断 REVIEW | 3/32 | 语义未确定，不能算正确或违规 |

已存在“信用卡付款，所以立即退款”的明确错误候选；也存在相同起点能正确说明 5–7 个工作日的轨迹。

## 3. 关键设计取舍：可核对的退款回执

### 3.1 新增的共同输出要求

在两臂完全相同的 system 补充要求中，要求最后一次退款告知提供一个结构化回执。
每笔订单包含：

| 字段 | 期望来源 |
|---|---|
| order_id | 实际目标订单 |
| status | 写入后订单状态，应为 cancelled |
| refund_amount | 此次取消新增退款记录的金额，按分精确核对 |
| refund_method_id | 原始付款账户与此次退款记录；不能仅猜“信用卡” |
| expected_refund_timing | 原付款方式为 gift_card：immediate；否则：5_7_business_days |

最终回执采用唯一 JSON 对象、唯一 orders 数组；拒绝重复键、重复订单、额外订单、多份互相冲突的回执。
数值必须有限，不接受 NaN/Infinity；金额归一化为分，拒绝多于两位的小数冒充精度容差。
此处定义数据合同，尚未生成可执行 schema 或修改 prompt。

补充要求只给字段定义、允许值和“依据工具与 Policy 填写”的要求，**不给当前任务的正确金额、账户或时效答案**。
格式本身奖励为零。正确回执的数值与支付分支才是目标。

### 3.2 必须明确的边界

- 这是新回执协议，不直接与旧自由文本的 30/32 或旧 reward 比较。必须重新测同协议 SFT 基线。
- 自由对话仍用于认证、询问原因和确认；不添加教师完成的历史前缀，不替模型完成业务动作。
- 回执正确不抵消前面错误承诺。最终评测需要检查全程退款声明及授权证据。
- 若预采样主要错误是 JSON 格式而非状态判断，本方案不启动 GRPO；那是协议学习问题，应先单独解决，不能把格式改善包装成业务改善。
- 此取舍须经用户确认；不能悄悄把“自由文本语义审计”换成“JSON 合规率”。

## 4. 数据：多实体、支付分支平衡

计划构造 **72 个合成取消订单实例：32 训练 / 8 开发 / 32 最终留出**。这是拟构造数量，目前不存在该数据集。
全部是 Task113 策略结构的派生实例，不称 tau2 官方新任务或工业真实订单。

每个实例保留两个 pending 目标订单与非目标状态订单；完整目标仍是取消该用户全部 pending 订单。
不引入退货、换货、条件改变意图或多次历史退款。每个待取消订单只含一条原付款记录，避免上游取消工具对复杂历史账目逐项退款的额外语义。

| 两笔目标订单原付款方式 | 训练 | 开发 | 留出 | 应答差异 |
|---|---:|---:|---:|---|
| 信用卡 / 信用卡 | 8 | 2 | 8 | 两笔分别原路退回，均 5–7 个工作日 |
| 礼品卡 / 礼品卡 | 8 | 2 | 8 | 两笔分别退原礼品卡，立即 |
| 信用卡 / 礼品卡 | 8 | 2 | 8 | 第一笔 5–7 天，第二笔立即 |
| 礼品卡 / 信用卡 | 8 | 2 | 8 | 第一笔立即，第二笔 5–7 天 |

这里的“第一/第二”只是设计表述；订单 ID、查询展示顺序和订单数组顺序均不能泄漏固定答案位置。
本轮不覆盖 PayPal；Policy 的“非礼品卡”规则不能因此宣称在所有支付类型上都已验证。

构造与隔离要求：

1. 每个独立实例使用不同用户、订单、支付账户、金额和认证信息；同一原始实体的改写及反事实版本不得跨 split。
2. 金额在两单间不同且与商品及支付记录一致；保持用户订单清单、订单归属、账户归属、礼品卡余额一致。
3. 留出实体不能来自已训练 SFT/GRPO 或已反复审计的用户与订单；须查全部模型祖先可用的数据清单，而不仅查最近 88 条。
4. 共享业务结构是本设计的限制；最多支持同结构、未见实体泛化，不支持未见策略结构泛化。
5. 独立任务/DB overlay；不修改上游 DB、任务原件或原始模型。用真实 Retail 工具重放 gold actions 校验初末状态，不手写伪造工具结果。
6. 冻结数据生成种子、实体映射、split、Policy、DB overlay、opening、用户模拟器配置与所有哈希。
7. 用户模拟器只接收其应知的用户信息，不接收 verifier 标签或希望产生的退款答案；不为获得 reward 方差刻意让用户纠错。
8. 最终留出集不参与样例选择、规则修补、reward 权重、prompt 或 checkpoint 选择。

## 5. 主指标、训练 reward 与保护指标

### 5.1 主指标：完整且准确的退款完成率

每条 rollout 定义三个条件：

- **B**：两单均正确取消；金额和原账户退款正确；没有非目标写入；完整正常结束。
- **C**：回执包含两单全部必要字段，均与实际证据一致；遗漏、错误金额/账户/时效、额外订单都不通过。
- **H**：授权与过程约束合格，且全程不存在与 Policy/状态冲突的退款承诺。需要证据，不能拿旧规则 PASS 代替。

主指标：`M = sum(B AND C AND H) / N`。

`N` 是冻结有效试验全集，不是只挑成功取消的样本，也不是只挑生成回执的样本。
模型早停、拒做、漏单、超出约定模型生成预算、格式错误都保留，不从分母移除。
基础设施 ERROR 单列；最多按相同身份/种子重试一次并保留两份产物。仍缺结果时，比较标记未完成，不能悄悄删一侧样本后发布。
REVIEW 不计已确认成功；另报“已确认成功—含全部待定的上界”。收益判断不得依赖把待定当成正确。

### 5.2 两层训练 reward：不再累加六类过程分

拟采用：`R = E × (0.5 + 0.5 × C)`。

- **E**：B 成立，且本轮限定流程的写前授权与禁止写入检查有可判定、合格证据。
- **C**：整份回执正确，二值判定；不分别给金额、格式、关键词、工具调用次数累计小分。

| 可确定的轨迹情形 | R |
|---|---:|
| 未完整执行、错误写入、明确未授权或提前结束 | 0 |
| 正确获授权完成取消，但回执错误或不完整 | 0.5 |
| 正确获授权完成取消，完整回执也正确 | 1 |

0.5 是预先固定的两层排序方案，不是“最优权重”。不会通过改权重来美化训练曲线。
确认语义不清或必要工具证据缺失时为 REVIEW/ERROR，不直接奖惩；在评分前停止当前批次，保留整组，不能只删低分轨迹补高分样本。
因此，授权可判定性必须在本轮预采样阶段验证。旧授权诊断不能直接复用为可靠标签。

明确限制：这是**轨迹级分层标量 reward，不是逐动作 credit assignment**。
例如 `[0, 0.5, 0.5, 0.5]` 中，三个回执错误的样本仍有正 advantage。不能声称三档评分已消除错误行为强化。
必须记录 `C=0 且 A>0`，并区分它来自“做对了业务”还是 verifier 误判。
若持续主要强化这类样本，本轮设计假设不成立，不能靠继续加步数掩盖。

训练 E/C 不等价于完整 H：尤其自由对话中的错误退款承诺仍需独立审计。
这是显式剩余的 reward–evaluator 差距；即使 R 上升，H 退化也不能通过验收。

### 5.3 不可牺牲的指标

- 原业务/终局成功率不能因学习回执下降。
- 未授权、错单/多单写入不得增加；新出现的关键违规逐条追溯，不能平均掉。
- 漏报时效、格式错误、提前结束、长度耗尽分别统计。
- “仅在 B 成功条件下的 C 正确率”作为定位指标，不能替代全量 M。
- 全量报告四种支付结构的结果，不能只发布容易改善的那一类。

## 6. 小规模预采样：决定是否值得投入训练

在看到模型结果前选定 8 个训练实例，每个支付结构 2 个。
每个运行 greedy 1 条与 stochastic n=4，共 **40 条 rollout**；不得按结果挑换任务。

启动条件是本次工程决策阈值，不是 GRPO 的普适定理：

1. 32 条随机样本无基础设施失败、超窗、未解析工具调用或长度截断；全部评分证据可判定。
2. E 至少 28/32，说明主要不是重新教模型完成取消流程。
3. 回执结构可解析至少 31/32；若主要瓶颈是格式，不启动这轮针对性 RL。
4. 至少 4/8 个组在 **E=1 且格式有效的样本之间** 同时出现 C=1 与 C=0；不能仅因早停/坏格式出现 reward 方差就通过。
5. 汇报 greedy、随机单条成功比例、8 个组的至少一条成功比例与各组 E/C/R/A，不把 n=4 采样的估计当成能力定论。
6. 对所有满分和所有“失败但正 advantage”逐条核对。已有错误承诺被奖满分、正常授权被误罚等已知关键错误必须修复并重新冻结，不能带进训练。

不满足时只报告哪个条件不成立；不自动扩大 n、换模型、增加 SFT 或换任务来追分。

## 7. 训练设置：复用已跑通的计算路径

| 参数 | 拟固定值 |
|---|---|
| 起点 | SFT100 中选出的 checkpoint30 合并模型，重新创建 LoRA；不续旧失败 GRPO |
| 模型证据哈希 | 2215F09DF8A8FF03B1CED725E7F87F7F953B4D0B91F5DDE1618628C1B036963C |
| 精度 / LoRA | BF16、非量化；r=16，alpha=32，dropout=0.05，原七类 projection |
| disable_dropout | false，显式保持已运行配置，不依赖新版库默认值 |
| 硬件目标 | 单 RTX 4090；只作为历史已运行参考，启动时重查真实 GPU/显存/模型文件 |
| num_generations | 4 |
| micro batch / accumulation | 1 / 8；每次更新真实消费两个新 n=4 组，共 8 条，不等于 n=8 |
| steps_per_generation | 4；运行时验证数据加载器和累积窗口，禁止 epoch 尾部偷跑更新 |
| 最大优化器更新数 | 50；总计 100 组、400 条新训练 rollout |
| learning_rate / beta | 2e-6 / 0.02，保留固定 SFT KL 参考 |
| temperature / top_p / top_k | 0.8 / 1.0 / 0 |
| loss_type / scale_rewards | dr_grpo / group |
| num_iterations / max_grad_norm | 1 / 1.0 |
| warmup / scheduler / optimizer | 2 updates / linear / adamw_torch |
| max_completion_length | 8192；保持观察 token 与模型 token 统计，不能用静默截断减显存 |
| 交互预算 | 8 用户轮、24 业务工具调用、32 工具迭代；须验证 gold 与预采样余量 |
| 用户模拟器 | 沿用现有提供商/配置角色，仅模拟用户，不参与 reward 裁决；启动前确认实际服务可用性 |

这不是重新挑一组“最优超参数”；保留历史计算路径，减少把 reward、学习率、KL、batch 一起改导致的不可解释性。
使用冻结种子打乱的任务轮转产生 100 个组，任务每轮覆盖一次；多出的 4 组按预定顺序，每种支付结构 1 组。
每组的任务、DB 初态、opening 与用户种子相同，四条 policy 采样不同；两组之间不做共同标准化。
模型 seed、任务采样 seed、每组用户 seed 和最终 eval seed 分开记录；用户 seed 不等于完整交互路径必定一致。

TRL 的 group advantage 与梯度累积是不同维度，beta 非零才启用其 KL 项；计算定义参考 [TRL 官方 GRPO 文档](https://huggingface.co/docs/trl/grpo_trainer)。实际执行继续绑定已核验版本与 trainer 源码，不自动升级到文档最新版。

## 8. 配对评测、工作量与停止条件

### 8.1 评测设置

- 开发集：8 实例，每个 2 个固定随机采样种子；SFT、step25、step50 各 16 条。
- 最终集：32 未见实体实例，每个 2 个固定随机采样种子；SFT 与选定 GRPO 各 64 条。
- 两臂 Policy、回执要求、初态、用户配置、解码温度及长度预算相同；无 Guard-only 增强、无重试挑好答案。
- 最终集只用于一次选定模型的报告，不展示给调参过程。按任务聚类的配对 bootstrap 95% CI，同时报告改善/退化/均正确/均错误的配对计数。
- 训练 seed 只有一个；两个 eval seeds 不能证明训练稳定性。显著性不足时如实称方向性开发结果，不称稳定泛化收益。

### 8.2 25-step 决策与选择

50 是训练上限，不是预设必须跑完才允许判断。
step25 使用开发集：若 M 没有高于 SFT，或终局成功率下降，或退款状态内容错误没有减少，停止本轮，不自动补后 25 步。
若通过，才在既定 50-step 日程下继续；需要保留 optimizer/scheduler/RNG 状态，不另起一个“25 步 warmup”混充续训。
step25/50 中只按开发集 M 选 checkpoint；必须满足业务与安全保护条件，平分取更早。无法满足时本轮不产生合格候选。
本停止策略偏向控制费用，可能错过较晚出现的收益；不得把早停失败推论为 RL 不可能有效。

发现以下情况在更新前或安全检查点停止：新关键误奖/误罚、非有限梯度、累积合同错误、系统失败、连续评分不可判定。
纯模型生成长度耗尽沿用显式 0 分政策并保留原始标记；不能把未结束的工具调用/放不下的 observation 当作普通 0 分绕过系统检查。

### 8.3 预算上限

| 工作 | 新 rollout 数 |
|---|---:|
| 8 实例 greedy + n=4 预采样 | 40 |
| 50 updates，两个 n=4 组/update | 400 |
| 开发集 SFT / step25 / step50 | 48 |
| 最终 SFT / GRPO 配对 | 128 |
| 合计，不含可解释的系统失败重试 | **616** |

不做 Terminal/Staged 两次 400 条训练。中途不满足条件，后续预算不消费。
历史单实例 400 条训练耗时 17921.5804 秒，约 4 小时 58 分；不能直接保证本轮耗时、显存或 API 成本相同。
云端开始前根据 40 条真实预采样的长度、耗时和 API 用量重新给出预算，再获取授权。

### 8.4 留存与图表

保留全部 prompt、对话、工具调用/结果、初末状态、回执、E/C 判据、raw reward、逐组标准化 advantage，以及实际模型/配置/种子哈希。
训练图固定为真实 `reward / reward_std / KL / loss` 四联图；另列 step0/25/50 的开发集 M、业务成功率、回执内容错误率及 `C=0 且 advantage>0`。
开发评测点之间只画点与连接线，不插值冒充逐步评测；原始 reward 点保留，平滑线标注窗口。50 次更新不生成假造的 100-step rolling mean。
训练中断时保留 optimizer、scheduler、RNG 和训练状态；回传完成须校验关键文件，不能把“模型目录存在”当成完整备份成功。

## 9. “有效果”的事先定义

工程目标为最终 M 提高至少 **10 个百分点**，同时终局成功率不下降、关键违规不增加。
完整 64 条/臂时至少净增 7 条才超过 10 个百分点。10 个百分点是目标，不是承诺或凭空计算出的可达值。

必须同时满足：

1. 对改善与退化的配对轨迹做盲化审核，检查真实状态、授权和全程退款声明，而不仅复用训练 scorer。
2. 两臂全部 128 条最终结果都保留；若 H 存在待定，报告下界/上界，不把待定自动清零来制造基线落差。保守差值为 GRPO 已确认成功下界减 SFT 可能成功上界。
3. 回执格式有效样本中的状态内容错误确实减少；若收益完全来自补 JSON 格式，不能称为退款状态判断能力提高。
4. 点估计达到目标但区间跨 0，结论是“该冻结开发样本上有正向点估计，证据仍不确定”；不宣称已稳定提升。
5. 只有 owner/开发者审核时，报告开发性结果与审核方式，不声称独立专家校准的正式 Verifier 指标。

若训练 reward 提高而 M 不提高，本轮不通过。若只降低退款时效错误但完整 M 不变，也不能改主指标来宣布成功。

## 10. 对抗式审阅：这套方案仍可能怎么失败

| 风险/刷分方式 | 设计中的检查 | 仍然存在的限制 |
|---|---|---|
| 全写“5–7 天”或全写“立即” | 四类支付结构平衡，混合两单逐单绑定 | 只验证已定义的支付分支，不是复杂推理 |
| 复制固定用户、金额、账户 | 实体隔离、金额变动、未见组合 | 同结构合成数据仍比真实业务窄 |
| 不回答/少做事避免出错 | 完整 M 固定分母；无完整执行 R=0 | R=0.5 的正确执行但错误告知仍可能有正 A |
| 回执对、前面对用户乱承诺 | 最终 H 审全对话，不只看 JSON | 训练 reward 未完整自动覆盖自由语义 |
| 规则抓到关键词即判成功 | 必需槽位、精确金额、账户与订单关系、重复/缺失/矛盾检查 | 新 parser 本身仍必须验证 |
| 把“受理退款”说成“钱已到账” | 字段是 expected_refund_timing，按 Policy 预期，不宣称银行实际到账 | tau2 没有真实银行到账时间证据 |
| GRPO 只学了回执格式 | 格式启动门槛、状态内容错误分解 | 若格式成为主瓶颈，应转协议/SFT 工作，另立实验 |
| 选择最好看的 seed/checkpoint | 开发集选点，最终固定配对，保留全部失败 | 一个训练 seed 不能证明可重复收益 |
| 用新规则给历史训练重评分制造提升 | 新协议重新取 SFT 基线，原历史分数不变 | 不能把新实验结论外推成旧 v7.1 成功 |

特别注意：0.5/1 两层 reward 也没有数学保证能使 M 上升。预采样信号、错误行为对应 advantage、冻结后效果必须形成证据链。

## 11. 实现差距与下一张任务的边界

当前不是“改一个配置就能开跑”：

- `RetailAgenticEnvironment` 已有 tasks_loader/environment_factory 注入口，但默认仍读取上游 retail registry。
- 当前 runner 的 dataset 把 task_split 写成 train，system prompt 使用既有包装；新 overlay 和回执协议尚未贯通预检、训练、评测。
- 当前退款 v2 是有限语义诊断：无候选直接 PASS，不能核验本设计的全量回执。
- 必须新建 opt-in 的任务/DB provider、回执校验、prompt 补充与独立配置；保持旧默认行为不变。禁止覆盖旧 reward 分数。

**用户确认设计后，下一张任务只做本地最小实现与离线验收，不启动训练：**

1. 构造并校验 72 实例、实体隔离清单及 gold 工具重放；不构造新教师自然语言轨迹。
2. 实现回执数据合同与 E/C 证据绑定，加入缺单、错金额、换账户、两单混绑、重复键、假取消、错误授权时序、gift/credit 时效颠倒等对抗测试。
3. 对原始 32 条基线及已知授权/退款误判做回归检查；只作为旧诊断缺陷测试，不把旧轨迹当新格式的成绩。
4. 校验新 provider 被训练和评测共同使用、状态重置隔离、assistant/tool loss mask 与真实两组累积合同。
5. 交付可预采样的最小载荷、命令与额度；另行申请上传、DeepSeek 用户模拟器和 GPU 授权。

本设计不授权继续下载/删除模型、修改云实例、启动 API、自动选新模型或自动训练。
