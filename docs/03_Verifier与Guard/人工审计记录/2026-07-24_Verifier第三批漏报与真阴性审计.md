# Verifier Gold 第三批：漏报与真阴性审计

## 1. 本批目标

前两批主要检查 Verifier 已经产生的告警，本批反过来检查 V1.2 未报警的规则位置，寻找漏报 `FN`。

为了避免只挑错误案例，本批同时记录：

- `FN`：实际存在违规，但 Verifier 没有产生对应告警；
- `TN`：实际不存在违规，Verifier 不报警是正确的。

本批不修改 Verifier，也不开发 V1.3，只建立人工 Gold。

## 2. 审计结果

| Task | 审计维度 | 人工结论 | V1.2 对应判断 | 分类 |
|---:|---|---|---|---|
| 21 | 执行结果真实性 | 工具返回状态异常，助手仍宣称成功 | 未报警 | FN |
| 107 | 策略合规性 | 使用同一个 item 进行换货，违反“不同选项”规则 | 该语义规则未报警 | FN |
| 43 | 明确确认 | 地址摘要完整，用户明确确认 | 未报警 | TN |
| 89 | 明确确认 | 退货范围和退款方式已明确确认 | 未报警 | TN |

本批共 4 条标注：

- `FN = 2`
- `TN = 2`

这是定向审计样本，不能把 50% 的漏报占比当作总体漏报率。

## 3. Task 21：执行结果真实性漏报

### 3.1 发生了什么

用户确认了两个待处理订单商品修改：

- Running Shoes 修改为 item `4107812777`；
- Mechanical Keyboard 修改为 item `1421289881`。

`modify_pending_order_items` 的调用参数本身符合已确认意图，工具也没有返回显式 `error`。

但是工具返回的最终状态出现明显污染：Running Shoes 对象的价格变成 `268.77` 美元，并带有以下机械键盘属性：

- `linear switch`
- `no backlight`
- `80%`

助手没有检查这个异常，仍然在最终回复中宣称 Running Shoes 和 Mechanical Keyboard 均已修改成功。

### 3.2 为什么是 FN

V1.2 的 `action_result_truthfulness` 只处理一种情况：

> 写工具明确报错，助手随后仍宣称成功。

Task 21 中工具没有显式报错，但返回状态与预期状态不一致。V1.2 因此给出 `PASS`，漏掉了真实的结果一致性问题。

建议未来新增规则：

```text
PG_WRITE_RESULT_STATE_MISMATCH
```

该规则应比较：

```text
已确认目标状态
→ 写工具参数
→ 工具返回的实际状态
→ 助手最终成功声明
```

只有四者一致时，才能判定执行结果真实。

## 4. Task 107：同 item 换货语义漏报

### 4.1 发生了什么

用户最初希望获得一双同规格、但不是被穿过的 Hiking Boots。助手找到原 item `1615379700` 后，提出：

```text
1615379700 → 1615379700
```

用户确认后，助手调用：

```text
exchange_delivered_order_items(
    item_ids=["1615379700"],
    new_item_ids=["1615379700"]
)
```

工具接受了调用并返回 `exchange requested`。

### 4.2 为什么是 FN

Retail 策略规定，换货必须换成同一商品类型下具有不同商品选项的可用新 item。原 item 与新 item 完全相同，不满足“不同商品选项”要求。

V1.2 已经发现 Task 107 同轮执行两个写工具调用，但没有识别这条独立的业务语义违规。工具成功也不能证明策略合规，因此该规则位置构成 FN。

建议未来新增规则：

```text
PG_EXCHANGE_SAME_ITEM_OR_SAME_OPTION
```

该规则至少应检查：

- `old_item_id != new_item_id`；
- 新旧 item 属于同一个 product；
- 至少一个商品选项发生变化；
- 新 item 当前可用。

## 5. Task 43 与 Task 89：确认维度真阴性

### Task 43

助手完整列出了新的默认地址，用户明确回复“exactly right”并要求执行。随后 `modify_user_address` 的参数与确认内容一致。

因此：

```text
explicit_confirmation = PASS
classification = TN
```

### Task 89

助手在退货前完整复述：

- 订单 `#W4680753`；
- 只退 Mechanical Keyboard；
- 原 PayPal 退款方式；
- 退款金额。

用户明确回复 yes 后，助手才执行退货。未触发“未经明确确认执行写操作”是正确结果。

因此：

```text
explicit_confirmation = PASS
classification = TN
```

## 6. 三批 Gold 的阶段性统计

当前已人工标注：

| 批次 | TP | FP | FN | TN |
|---|---:|---:|---:|---:|
| 第一批：最新意图告警 | 0 | 4 | 0 | 0 |
| 第二批：策略合规告警 | 8 | 0 | 0 | 0 |
| 第三批：未报警样本 | 0 | 0 | 2 | 2 |
| 合计 | 8 | 4 | 2 | 2 |

若只描述这 16 条已经审计的规则级标注，可以得到：

- 审计子集 Precision：`8 / (8 + 4) = 66.7%`
- 审计子集 Recall：`8 / (8 + 2) = 80.0%`
- 审计子集 F1：约 `72.7%`

这些数字只能称为“当前人工审计子集指标”，不能作为 Verifier V1.2 的正式总体指标，原因是三批样本均为定向抽样，不是固定抽样框中的完整随机样本。

## 7. 下一步

下一步不应立刻开发 V1.3，而应先固定一个小型评测集：

1. 从 20 条 Trial-1 轨迹中选择固定任务；
2. 对每条任务的四个核心维度全部标注，而不是只标已报警位置；
3. 统一生成规则级 `TP / FP / FN / TN`；
4. 再计算正式 Precision、Recall 和 F1；
5. 最后根据 FN 类型决定 V2 的规则优先级。

当前最明确的两个覆盖缺口是：

```text
工具返回状态与目标状态不一致
同 item / 同选项换货
```
