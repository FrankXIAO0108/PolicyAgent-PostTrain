## 2. 结论摘要

P0 当前可以作为以下用途：

1. 严格评测数据契约和原子谓词的工程基线；
2. 对已有轨迹执行只读工具调用与回合协议诊断；
3. 在新 rollout 同步保存完整状态和语义绑定后，执行任务级严格评测。

P0 当前不能用于以下用途：

1. 生成 Base/SFT/RL 三方严格通过率；
2. 把影子诊断分数解释为模型能力指标；
3. 直接充当 GRPO Reward；
4. 扩展到 Baseline20 后宣称正式指标；
5. 将任务编号等同于唯一、固定的最终用户意图。

原因不只是历史轨迹缺少 sidecar。Task 59 证明：动态用户模拟器可能在同一任务编号下产生不同的合法意图分支。静态绑定某一条轨迹最终意图的 rubric，不能直接横评其他 rollout。

## 4. Tau2 与严格谓词差异审阅

### 4.1 Task 59 Base：不是一个可采信的严格分歧

原始轨迹中：

- 用户在消息 15 明确确认取消 `#W2702727`，同时要求修改该订单地址；
- Agent 先取消订单，再尝试修改该已取消订单的地址，工具返回失败；
- 用户随后在消息 23 明确确认修改 `#W8268610` 的地址；
- 第二次地址修改成功。

P0 rubric 把“最终意图”固定为“取消 `#W2702727` 且不修改任何地址”，因此把两次地址写入都判为 forbidden。该规则与这条实际对话不一致。

评审结论：

- `address_write_forbidden_after_cancellation_choice=FAIL` 属评测器假阳性；
- 但 Base 仍存在真实的规划/顺序问题：承诺在同一订单上同时取消和改地址，且在取消后才尝试改地址；
- 正确处理应先指出两个动作相互冲突并要求用户二选一，而不是执行一个后让另一个由工具报错；
- Tau2 reward=0 与“轨迹存在问题”的方向可能一致，但不能拿当前错误谓词证明其原因。

### 4.2 Task 59 SFT：明确的 P0 假阳性

该 SFT rollout 的用户最终要求：

- 修改 `#W2702727` 地址；
- 取消 `#W8268610`；
- 两项操作均经过后续用户明确确认。

Agent 实际执行与该分支一致，Tau2 reward=1。P0 仍按另一条轨迹的固定结论禁止地址修改，因此产生 FAIL。

评审结论：当前 Task 59 rubric 不具备跨 rollout 可移植性。该 FAIL 不能归因于模型，必须记为评测器假阳性。

### 4.3 Task 107 SFT：Tau2 的 Policy 盲点

Tau2 reward=1，但严格谓词发现：

- 消息 18 同时包含用户文字与 `get_product_details`；
- 消息 20 同时包含用户文字与 `get_product_details`。

Retail policy 明确要求“回复用户”和“调用工具”不能处于同一条 assistant 消息。该检测直接来自原始消息结构，不依赖缺失 sidecar。

评审结论：这是可信的 Policy 违规，也是 Tau2 task reward 的覆盖盲点。业务严重度可记为低，但在严格 Policy 口径下不能算全通过。该信号适合作为过程诊断；在完成跨轨迹校准之前，不应直接作为高权重 RL 惩罚。

### 4.4 其余结果

Task 24、50 没有观察到确定性 FAIL，但这不等于严格通过。Task 107 Base 的工具参数与成功规格不一致，但严格状态谓词因缺状态证据返回 ERROR。所有 ERROR 均表示评测证据不足，不是模型失败。

## 5. 假阳性与假阴性风险

### 假阳性风险

1. **轨迹特定意图被错误提升为任务级规则**：Task 59 已实际发生。
2. **用户模拟器分支漂移**：同一 task ID 的 Base、SFT、RL 可能收到不同的后续选择和确认。
3. **协议违规严重度混同**：轻微消息格式违规与错误写数据库都导致 strict pass=false，若直接用作 Reward 会失去严重度信息。
4. **历史任务规格与当前 rollout 不绑定**：只校验 task ID，不校验实际用户消息/意图绑定哈希，会造成错误归因。

### 假阴性风险

1. 历史产物缺少 `initial_state`、`final_state`，状态错误无法完整检测；
2. 缺少 `confirmation_message_index_by_call_id`，无法验证写操作是否绑定最终确认；
3. 缺少 `latest_intent_revision_message_index_by_call_id`，无法可靠判断晚期意图变化；
4. 缺少与最终回复 SHA256 绑定的 `claim_checks`，无法确定最终声明是否真实；
5. ERROR 不会变成 FAIL，这是正确的归因纪律，但意味着当前影子评测覆盖率不足。

## 6. P0 校准与扩展决策

当前决策：**P0 工程实现保留，但校准不足，不扩展到 Baseline20，不进入 Reward。**

下一次完整 Base/SFT/GRPO 对照必须在 rollout 时同步保存：

1. 初始与最终数据库状态及哈希；
2. 原始消息和工具结果；
3. 每个写调用绑定的最终确认消息索引；
4. 每个写调用绑定的最近意图修订索引；
5. 最终回复 SHA256 与结构化 claim-check；
6. task ID 之外的实际意图分支标识或轨迹规格哈希；
7. Tau2 reward、严格谓词结果和基础设施状态三套独立字段。

rubric 需要拆成两层，但本轮不实施：

- **任务不变量**：身份验证、工具存在性、一轮一工具、消息/工具分离、工具成功状态等；
- **轨迹绑定变量**：最终取消目标、地址目标、确认覆盖范围、最终声明等，由当前 rollout 的结构化 sidecar 提供。

## 7. 闭环含义

本轮完成的是“评测工程闭环”的 P0：规则定义、对抗测试、冻结产物影子回放、差异复核和限制决策。

它不是“模型训练效果闭环”。模型闭环仍需后续同协议运行：

`同一 SFT checkpoint → 同一任务/采样协议 → 短程 GRPO → 完整证据 sidecar → Tau2 + 严格评测 → badcase 分析`

在该模型闭环完成前，不讨论指标提升，也不宣称 RL 优于 SFT。
