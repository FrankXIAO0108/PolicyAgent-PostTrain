# Verifier V1.2 规则级人工 Gold 标注——第二批

## 一、标注范围

本批次审计 Verifier V1.2 的 `policy_compliance`（策略合规性）告警，选取 Task 1 和 Task 109 中 8 条具有代表性的告警。

本批次覆盖四种典型情况：

1. 单个只读工具调用与用户可见文本出现在同一轮；
2. 同一轮发出多个只读工具调用；
3. 单个写工具调用与用户可见文本出现在同一轮；
4. 同一轮发出多个写工具调用。

标注单位是一条 Verifier 告警，而不是整条任务轨迹。某条轨迹获得 benchmark reward，也不代表它在策略合规维度没有问题。

## 二、判定依据

本批次使用的 Retail 策略包含两条明确约束：

1. 每个助手轮次最多调用一个工具；
2. 如果该轮调用工具，就不能在同一轮同时向用户回复文本。

因此：

- 用户明确确认了两项操作，只能说明两个写操作的内容都获得授权；
- 它不能覆盖“每轮最多一个工具调用”的执行时序要求；
- 多个只读调用和多个写调用都属于真实违规，但风险等级不同。

本批次严重程度口径：

| 情况 | 人工严重程度 |
|---|---|
| 多个只读工具调用 | `MINOR`（轻微） |
| 工具调用同轮附带用户可见文本 | `MINOR`（轻微） |
| 多个写工具调用 | `MAJOR`（严重） |

## 四、逐条审计结论

### Task 1：只读工具的调用结构

Task 1 的事件 9 同时调用：

- `get_order_details`
- `get_user_details`

事件 12 又同时对两个商品调用两次 `get_product_details`。

这些调用都是只读查询，不会改变订单状态，因此风险低于多个写操作；但它们仍然明确违反“每轮最多一个工具调用”的规则，应保留 `MINOR` 告警。

此外，事件 5、9、12、21 均在工具调用轮输出了用户可见的过程说明，例如“我来查找用户”“我来检查订单信息”等。这些内容即使没有造成语义错误，也违反工具调用与回复文本互斥规则，应标为 `MINOR` 真阳性。

### Task 109：同轮执行两个地址写操作

用户明确确认了两项修改：

1. 将账户默认地址更新为新地址；
2. 将订单 `#W1603792` 的收货地址修改为同一地址。

助手随后在同一轮调用：

- `modify_user_address`
- `modify_pending_order_address`

两项写操作的内容与用户意图一致，因此这里不是“未经确认”问题。真正的问题是执行时序：同一轮发出两个会改变系统状态的调用，违反每轮最多一个工具调用的限制。

多个写操作还存在额外风险：如果其中一个成功、另一个失败，系统可能进入部分完成状态。因此，`PG_TOOL_CALL_CARDINALITY` 在该事件中判为 `MAJOR` 是合理的。

同一轮还包含“现在执行两项地址更新”的用户可见文本，所以 `PG_MESSAGE_TOOL_EXCLUSIVITY` 也成立；但这条格式告警本身仍保持 `MINOR`，避免和多个写操作的严重风险重复升级。

## 五、与第一批 Gold 的关系

第一批 Gold 审计的是 `latest_intent`：

- 重点判断写操作参数是否得到用户确认；
- 4 条告警均因内部 ID 与用户可见实体映射不足而构成误报。

第二批 Gold 审计的是 `policy_compliance`：

- 重点判断工具调用的数量和轮次结构是否合规；
- 8 条告警均由原始轨迹直接支持，构成真阳性。

这说明当前 V1.2 的不同规则质量差异明显：

| 规则维度 | 当前定向样本表现 | 初步判断 |
|---|---|---|
| `latest_intent` | 0 TP / 4 FP | 实体映射和跨轮状态继承仍需修复 |
| `policy_compliance` | 8 TP / 0 FP | 结构规则在本批样本中可靠 |

不能把两个批次直接合并为整体性能指标，因为它们都是面向已触发告警的定向抽样，并未覆盖未报警样本。

## 六、下一步

Verifier V1.2 继续冻结，不开发 V1.3。

下一批应优先补充两类样本：

1. `policy_compliance` 的更多任务与边界情况，验证当前 100% 是否只是样本选择造成；
2. Verifier 未报警的轨迹片段，用于寻找漏报并计算召回率。

完成这些审计后，才能形成可报告的规则级 Precision、Recall 和 F1。
